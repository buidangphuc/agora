## Context

team-identity is a gRPC service (`:50053`) plus a tiny JWKS HTTP listener (`:50063`). It owns `identity_db` (users, addresses, password reset tokens, sessions, login history, outbox), issues RS256 JWTs, produces `identity.events` through a transactional outbox, calls team-audit before `SetUserStatus`, and sweeps old sessions. Main today carries Q1 session continuity (refresh rotation, reuse detection, grace replay, `revoked_at`), login and refresh enforcement, user status, and the retention sweeper; all of it wins over `origin/feat/go-sdk-v1-e2e` (reference only).

## D3 Migrations run through `server migrate up`, never at boot

The binary keeps one entry point and gains a subcommand: `cmd/server/main.go` dispatches on `os.Args[1] == "migrate"` with `os.Args[2] == "up"` to `app.Migrate(ctx, settings)` and exits 0 or non-zero; any other `migrate` argument prints a usage line and exits non-zero; no argument runs the service. `app.Migrate` loads `config.LoadMigrate()` (an SDK `Runtime` plus `Postgres` group only, so the Job needs `ENV` and `DATABASE_URL` and not the JWT key or Kafka) and calls `migrate.Up(ctx, s.Postgres.URL, store.Migrations())`; a failure or dirty state returns an error (the SDK names the dirty version). `app.Run` never migrates: it opens Postgres, registers health and serves, so a schema that is not migrated fails calls, not boot. Applying `0001`-`0019` leaves version 19; golang-migrate parses the leading digits as the version, so `0001`-`0008` keep versions 1-8 and a database migrated by the old compose job needs nothing. golang-migrate holds an advisory lock, so two concurrent runs migrate once. Deploy track (change `deploy-go-sdk-v1`): compose keeps a `team-identity-migrate` service that runs the service image with the argument `migrate up` (the service `depends_on` it with `service_completed_successfully`), and gitops runs an Argo PreSync Job per service with the same image and arguments. `make migrate` from `go-service.mk` (`go run ./cmd/server migrate up`) now works as is. Rejected: migrating at boot (replicas race the lock and a bad migration restarts pods in a loop), and a separate migrate image (two artifacts to keep in step).

## D4 Outbox over the existing table

The table `identity_outbox_events` keeps its name and its pending rows. SDK `outbox.NewStore(pool, "identity_outbox_events")` needs `seq`, `topic` and `traceparent`. Migrations `0009`-`0018` are `outbox.UpgradeSQL("identity_outbox_events")` split one file per step in the same way as `payment-go-sdk-v1` D4: Prepare (0009), Backfill (0010), Switch (0011), the NOT NULL check, validate and set-not-null steps (0012-0014), one `CREATE INDEX CONCURRENTLY` per file (0015-0017) and the `claim_idx` drop (0018); test `TestOutboxMigrationsEqualUpgradeSQL` concatenates the statements of `0009`-`0018` and compares them with `UpgradeSQL`. Migration `0019_outbox_requeue_and_unify` follows, in one transaction, with two statements: `UPDATE identity_outbox_events SET status='pending', attempts=0, available_at=now(), locked_until=NULL, error=NULL WHERE status='failed'` and `UPDATE identity_outbox_events SET aggregate_type='User' WHERE status<>'published'`; its down file is a no-op `SELECT 1` (data fix, nothing to undo). The first statement answers the SDK warning on `outbox.SchemaSQL`: rows the old relayer parked as `failed` after `OUTBOX_MAX_ATTEMPTS` (10) would block their aggregate under the SDK relayer, and a parked `SessionRevoked` was never denylisted at the gateway, so they are requeued once, by the migration, before the new relayer starts (the migrate Job runs before the new pods; the relay is at-least-once and `event_id` is the dedupe key, so a requeued row that the gateway already saw is harmless). The second statement gives every unpublished `Session` row the `User` aggregate, so per-user order between an old pending `SessionRevoked` and a new `UserStatusChanged` holds regardless of drain state (`seq` was backfilled in `created_at` order by `0010`). Rows later parked by the SDK relayer (permanent record error) are not touched by a re-run, because a migration runs once. Deploy order (human decision, Round 2): the first rollout scales the old pods to 0 before the PreSync migrate Job and the new pods start (a Recreate rollout once, never two relayers), so `0019` requeues the parked rows while no relayer runs and the old image's relayer, which ignores `seq`, never overlaps the SDK relayer. The README documents it and names the equivalent SQL for an operator who prefers to requeue by hand (`UPDATE ... WHERE status='failed'`) or delete the rows. Later rollouts use the normal strategy.

Enqueue: the domain keeps its `OutboxRow` and `EnqueueFn` types (the row is built inside the write transaction); the `store` converts to `outbox.Row{EventID, AggregateType: "User", AggregateID: userID, EventType, Payload: envelope bytes, RequestID}` and calls `EnqueueTx(ctx, tx, row)` on the transaction that wrote the session or status change, so the atomicity scenarios (`TestSetUserStatusRollsBackOnOutboxFailure`, `TestReuseOutboxFailureRollsBack`) stay valid. `Topic` is empty, so the relayer default `IDENTITY_EVENTS_TOPIC` applies. Envelope bytes and `event_id` are unchanged. Today `SessionRevoked` rows use `aggregate_type` `Session` and `UserStatusChanged` rows use `User`, both keyed by the user id. The SDK orders per `(aggregate_type, aggregate_id)`, so that split would drop the guarantee that `UserStatusChanged` follows the `SessionRevoked` rows of the same call (spec `user-enforcement`, "Events keep per-user order"). New rows of both types therefore use `aggregate_type` `User`; unpublished rows written by the old image are moved to `User` by migration `0019`. No consumer reads the column.

Behaviour changes (accepted): no attempt limit (the old `OUTBOX_MAX_ATTEMPTS` parked a row after 10 transient failures, and those already-parked rows are requeued by `0019`; the SDK retries forever and parks only permanent record errors, and logs at ERROR after `AlertAfter` attempts); the claim lease is `OUTBOX_CLAIM_LOCK` (duration). Rejected: keeping the local relayer (two implementations of the same ordering rules).

Purge (human decision, Round 2): published rows are deleted after 7 days. `app` builds a second ticker, `lifecycle.Every(s.Outbox.PurgeInterval, purgeTick, lifecycle.RunAtStart(), lifecycle.WithLogger(logger))`, where `purgeTick` calls `store.Purge(ctx, s.Outbox.PurgeRetention)`, logs `rows_purged` only, and returns nil after a warning on error. Both durations are service settings (`OUTBOX_PURGE_RETENTION` 168h, `OUTBOX_PURGE_INTERVAL` 1h, each > 0) in a service `OutboxPurge` group, because the SDK `Outbox` group has no purge keys. The component stops with the sweeper, before the pool closes. `Purge` only deletes `status='published'` rows, so pending and parked rows stay.

## D5 Audit through `auditx`

`auditx.Dial(s.Audit, "service-team-identity", "audit.write")` returns a lazy connection; `UPSTREAM_AUDIT_ADDR` is required in every ENV (human decision, Round 2: upstreams the service uses have no fallback mode), so `config.Load` refuses an empty address and there is no nil connection or nil writer path. `upstream.NewAuditWriter(conn)` returns an adapter that maps `auditx.Event` to `WriteAuditEventRequest`. `AuthService` holds `*auditx.Gate`, built with `auditx.NewGate(writer, logger)` and required (constructor error on nil gate). `SetUserStatus` calls `gate.Do(ctx, event, func(ctx) error { return repo.SetStatus(...) })`, so the write precedes the change and any write error or timeout returns `Unavailable` `audit trail unavailable` without calling the action. The existing order is kept: validate, load target, refuse self and admin target, then the gate. The audit event content is unchanged (`actor_id` from the principal, `user.set_status`, `user`, target id, metadata `status`, `reason_code`, `note`, `until`). The `reflect`-based nil check (`auditConfigured`) is deleted.

## D6 Health: Postgres only

`health.Register("postgres", postgres.Checker(pool))`. Kafka is not registered, here or in any service (human decision, Round 2: readiness is Postgres and required upstream checks only): identity is the only login path, the outbox makes Kafka asynchronous, and a broker outage must not make every pod NotReady and stop sign-in. The relayer logs and backs off, and the pending rows are observable through `outbox.Store.Stats` later. `liveness` is served by `healthx` independent of the checks; gitops sets `probes.livenessService: liveness`. Rejected: also registering `kafkax.Checker` as payment does (payment reads a topic it must consume; identity only produces and tolerates delay).

## D7 Auth and errors

Handlers start with `auth.RequirePrincipal`, `auth.RequireScopes(ctx, "admin")` (account admin), `auth.RequireService(ctx, "identity.read")` (profiles) or `auth.RequireUser` (self-scoped RPCs that today answer `PermissionDenied` `user principal required`). `Login`, `Register` and `RefreshSession` call none (public). The `commonv1.Principal` used for event envelopes is built from `auth.Principal` in `rpc`. One `grpcx.ErrorTable` lists, in order: `ErrAccountLocked` -> `PermissionDenied` `tài khoản bị khóa`, `ErrInvalidCredentials` -> `Unauthenticated` `invalid credentials`, `ErrUsernameTaken` -> `AlreadyExists` `username already exists`, `ErrInvalidInput` -> `InvalidArgument` `invalid input`, reset-token errors -> `InvalidArgument`/`NotFound` with their current texts, `ErrUserNotFound`, `ErrAddressNotFound`, `ErrSessionNotFound` -> `NotFound`, `ErrStatusPrecondition` -> `FailedPrecondition`, `ErrAuditUnavailable` is gone (the gate returns a status already, passed through unchanged), invalid or expired refresh token -> `Unauthenticated` with the generic refresh text, `ErrRefreshUnavailable` -> `Unavailable` `service unavailable`. A `23505` that no sentinel claims falls to the SDK `AlreadyExists` rule; `Canceled` and `DeadlineExceeded` are the SDK mapping; anything else is `Internal` `internal error`, logged server-side without driver text reaching the caller. The old `internalErr` helper is deleted.

`ClientFromContext` (the gateway-computed `x-client-ip`, `x-client-user-agent` metadata) stays in `rpc` and is audit-only data, never part of authorization.

## D8 JWT, JWKS and signing key

`token.Signer` keeps `golang-jwt/v5` for RS256 (`jwtx` has wire types only). Claims are built as `jwtx.Claims{Name, Type, Scopes, SessionID, Subject, IssuedAt, ExpiresAt}`, marshalled and signed as `jwt.MapClaims` so claim names come from one contract; `typ`, `scopes`, `sid` (omitted when empty) are unchanged. `BuildJWKS` returns `jwtx.JWKS` with `jwtx.JWK` (same field order: `kty`, `use`, `alg`, `kid`, `n`, `e`), so the served bytes equal today's. `JWKSHandler` keeps its path, method rules and `Cache-Control`. `app` serves it with `lifecycle.HTTP(&http.Server{Addr, Handler, ReadHeaderTimeout: 5s}, s.ShutdownGrace)` on `JWKS_HTTP_PORT`. The boot guard stays and now sits in two places: `Settings.Validate` calls `RequireNonDevSigningKey` when `Runtime.IsStrict()` (the same four spellings as the old `hardenedSecretEnvs`), so `config.Load` reports it joined with the other strict refusals (empty `LOG_KEY_FP_SECRET`, `KAFKA_BROKERS`, reflection, expose-token) and the existing platform-e2e boot-guard steps, which start the real image with compose env plus `ENV=production` and look for `refusing to start` and `JWT_KID`/`JWT_PRIVATE_KEY` in the log, still find them although compose sets no `LOG_KEY_FP_SECRET`; and `app.Run` calls `NewSigner` then `RequireNonDevSigningKey` again before any connection, so a caller that builds `Settings` by hand is guarded too. The error text is `refusing to start: JWT_KID is the development key id` or `refusing to start: JWT_PRIVATE_KEY is the committed development key` and never contains key material. An unparsable key is not a `Validate` concern (left to `NewSigner`, any ENV). `IsProd()` and `RequiresHardenedSecrets()` are deleted. Rejected: verifying tokens in identity (the issuer never verifies; the edge does).

## D9 In-memory repositories as test fakes

`internal/store/storetest` holds the in-memory user, session, address and outbox fakes; they serve `identity` and `rpc` unit tests and the parity tests against Postgres. `TestServerBinaryExcludesFakes` runs `go list -deps ./cmd/server` and fails if `storetest` is linked, so a fake cannot return as a runtime fallback. Postgres tests use `testkit.Postgres(t)` and run in `make check` with `GO_SDK_REQUIRE_DOCKER=1`; they fail, not skip, without Docker. The unreachable-database boot test needs no Docker (closed local port). A Docker-backed test that skips is a gate failure (human decision, Round 2); `GO_SDK_REQUIRE_DOCKER=1` makes the harness fail instead of skip.

## D10 Sessions are required

`identity.NewAuthService(users, sessions, signer, ttl, gate)` takes the session store and gate as required arguments and returns an error for nil. The spec "Sessions disabled yields no refresh token" described a service built without sessions that is not a deployable configuration (`auth` already requires that a login without a recorded session fails). Login and Register always create a session and return a refresh token; a nil store or gate is a construction error only. The scenario titles `Sessions disabled yields no refresh token` and `Session retention: disabled sweeper` are kept in the MODIFIED blocks so archive can match them, with their content rewritten to the new behaviour.

## D11 Sweeper as a ticker component

`lifecycle.Every(s.Retention.SweepInterval, tick, lifecycle.RunAtStart(), lifecycle.WithLogger(logger))`. `tick` calls the existing `SweepOnce`, logs counts only (`sessions_purged`, `login_events_purged`) and returns nil after logging a warning on error (so the SDK does not log error text), so the next tick retries. `lifecycle.StopAfter(grpcx.Serve(...), relayer, sweeper, purger)` stops the relayer, sweeper and outbox purger after the server, and the pool is closed last by `stack.Close`. Existing config validation for `SESSION_RETENTION`, `LOGIN_HISTORY_RETENTION`, `SESSION_SWEEP_INTERVAL`, `SESSION_SWEEP_BATCH_SIZE` > 0 stays in `Settings.Validate`; unparsable values fail in the SDK loader with the variable named.

## D12 Relay log redaction

The SDK relayer logs `aggregate_id` (the user id) on failed rows. `events.RedactingHandler(inner, fp *kafkax.Fingerprinter)` wraps the slog handler given to `outbox.RelayerOptions.Logger`: for any record attribute `aggregate_id` it emits `key_fp` instead, 12 hex of HMAC-SHA256 under `LOG_KEY_FP_SECRET`. The fingerprinter comes from `kafkax.NewFingerprinter(s.LogKeyFP.Secret)`. The secret is required in a strict ENV and defaults to the SDK local value otherwise. Rejected: setting `AggregateID` to a pseudonym (it is the Kafka partition key the gateway relies on for per-user order).

## D13 SDK packages not used

`idempotency` (registration and login are not retried by the gateway; reuse detection is its own mechanism), `flags` (no feature flags), `resilience` (the only outbound call is the audit write, bounded by the gate), `consume` (identity consumes nothing), `mockdata` (no external adapter: Postgres, Kafka and team-audit are the real dependencies; the old "no Kafka" and "no audit" modes were the fallbacks the user removed), `upstream` (used only through `auditx.Dial`), `pagination.EncodeOffset`/`DecodeOffset` (the login-history cursor is a decimal offset and `ListUsers` uses the last username; both are wire formats the clients echo back unchanged; only `Clamp` is used).

## D14 Compatibility of ports and names

`GRPC_PORT` 50053, `JWKS_HTTP_PORT` 50063, the Dockerfile `ENV GRPC_PORT=50053` and the binary name `server` are unchanged. Ports are not touched.
