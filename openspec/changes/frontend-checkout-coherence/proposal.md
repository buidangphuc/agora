## Why

Checkout shows one summary for a multi-shop cart: one shipping fee computed on the whole subtotal, one voucher validated against the first shop, no delivery date. team-order already charges per shop group, so the screen and the charge disagree (backlog Q11, Q12 ETA and address parts, Q18; `buyer-journey.md` #2, #3, #8, #10). After placing, only the first order gets a payment transaction, so the other orders of a checkout cannot be paid ("Thanh toán ngay" ends in a 404). The buyer also never sees at confirm which address CreateOrder will use.

initiative: q11-checkout-coherence

depends_on: order-multishop-checkout (provides `OrderService.PreviewCheckout`, `CreateOrderRequest.shop_vouchers` / `platform_voucher_code` / `confirmed_address`, `Order.checkout_id` / `platform_voucher_code` / `platform_discount_amount`, and the `estimated_delivery_at` of `CalculateShippingFee`; its transitive dependencies are promotion-voucher-scope and order-address-eta). A buyer with addresses but no default who sends an empty `address_id` gets FAILED_PRECONDITION "address not found" from team-order (no first-address fallback, C9); this slice shows the same fixed message as any "address not found". `PaymentService.CreatePayment`, `GetPayment`, `ProcessMockPayment`, `OrderService.ListBuyerOrders`, `GetOrder` are consumed unchanged; no team-payment change. `team-frontend/proto` and `src/generated` are regenerated from platform-core, never edited by hand. No new dependency.

## What Changes

- **Per-shop checkout groups from the server.** The checkout page (`src/app/(checkout)/checkout/(summary)/page.tsx`) replaces `calculateShippingFee(address.city, cart.subtotal)` + `previewVoucher(code, cart.subtotal, firstSeller)` + `orderTotal(...)` by one `previewCheckout` call (new wrapper in `src/lib/gateway/orders.ts`, calls `OrderService.PreviewCheckout` with `address_id`, `item_ids`, shop vouchers, platform voucher). It renders one group per `CheckoutGroupQuote` (shop name, lines, subtotal, shipping or "Freeship", shop discount, platform-voucher share, group total, "Nhận hàng dự kiến dd/mm") and a summary whose rows are the response totals. The frontend adds nothing up: `orderTotal` is no longer used for checkout (the function stays for other callers) and `OrderSummary` takes the server figures. If `PreviewCheckout` fails the page throws to `error.tsx` (no total is ever shown without the server); FAILED_PRECONDITION "cart is empty" redirects to `/cart`.
- **Scoped vouchers.** URL state: `sv=<sellerId>:<CODE>` (repeatable, at most one per seller) and `pv=<CODE>`; the legacy `voucher` param is dropped (a stale link simply has no voucher). `VoucherModal` becomes a per-group shop-voucher field (suggestions from `listVouchers(sellerId)`) plus one platform-voucher field (suggestions: `listVouchers` entries whose scope is PLATFORM). The preview's `VoucherQuote` decides: `valid=false` shows its `reason` under the field and the totals already exclude it; only codes with `valid=true` are carried to the confirm step and sent in `CreateOrder` (`shop_vouchers`, `platform_voucher_code`; the legacy `voucher_code` is never sent). `previewVoucher` and the first-seller voucher logic are removed from the checkout path (the function stays for other callers).
- **Delivery promise.** PDP `ShippingInfo` adds "Nhận hàng dự kiến dd/mm" for a signed-in buyer with a default address, from `estimated_delivery_at` of the existing `CalculateShippingFee(city, 0)` call; `calculateShippingFee` (wrapper) returns `estimatedDeliveryAt` (ISO string or `null`). Each checkout group shows its own date from `CheckoutGroupQuote.estimated_delivery_at`. dd/mm is formatted in Asia/Ho_Chi_Minh by one helper (`src/features/order/deliveryDate.ts`); the frontend never computes "today + n". Anonymous visitors, buyers without an address, `shipping_quoted=false`, an unset timestamp or a failed call show no date and no placeholder.
- **Address integrity.** Confirm shows the address from `PreviewCheckout.shipping_address` and `PlaceOrderForm` sends it as `confirmed_address` with the `address_id`. `checkoutAction` maps `ConnectError` `FAILED_PRECONDITION` with `rawMessage` containing `address changed` to a fixed message and `addressChanged: true` (the form calls `router.refresh()` so the new address and totals show, and unlocks); `address not found` to a fixed message with a link back to the address step; `UNAVAILABLE` to a fixed retry message. Every other error keeps the existing generic handling. Fixed Vietnamese constants, never the server string.
- **Every online-pay order payable.** `checkoutAction` no longer calls `createPayment` for the first order; for an online method it returns `paymentUrl = /checkout/pay/<orders[0].id>`, COD goes to `/account/orders?success=1` as today. The pay page (`pay/[id]/page.tsx`): when `getPayment` finds none and the order is `PENDING` with an online method, it calls `createPayment(order.id, order.paymentMethod)` (idempotent per order) and shows the result; a COD, non-PENDING or not-owned order with no transaction is still 404. After the payment succeeds the simulator offers "Thanh toán đơn tiếp theo" to the next unpaid order of the same `checkout_id` (`ViewOrder.checkoutId`, from `ListBuyerOrders`: same `checkout_id`, `PENDING`, online method, lowest `sellerId`), until none is left. This makes "Thanh toán ngay" on `/account/orders` work for an order without a transaction.
- **`items` pass-through (owned by frontend-cart-selection for the cart side).** `checkoutParams` gains `items` (comma-separated cart item ids), kept by `checkoutHref` across all steps and sent as `item_ids` to `PreviewCheckout` and `CreateOrder`. Empty = whole cart. This slice adds no cart UI; the empty-selection redirect and "Quay lại giỏ hàng" with selection belong to frontend-cart-selection (the `/cart` redirect on "cart is empty" above is what that slice relies on).
- **Gateway routes called by the frontend** (checked against `team-gateway/internal/edge`): `CalculateShippingFee`, `CreateOrder`, `GetOrder`, `ListBuyerOrders` (order.go), `CreatePayment`, `GetPayment`, `ProcessMockPayment` (payment.go), `ListAddresses` (address.go), `ListVouchers`, `GetCart`, `AddToCart` all have forwarders. `PreviewCheckout` has none yet: its forwarder is owned by the upstream slice order-multishop-checkout (decided in round 1); this slice adds no gateway code and its e2e fails at the first checkout scenario if the forwarder is missing.
- Tests are colocated vitest; e2e in `platform-e2e/tests/e2e/features/frontend/checkout_coherence_ui.feature` (new). `team-frontend/FEATURES.yaml` is left for the e2e-author.

## NFR

- Checkout page: one `PreviewCheckout` per render replaces one `CalculateShippingFee` + one `ValidateAndReserve`; server-side budget p95 <= 300 ms for <= 5 groups (team-order). The page adds at most one `listVouchers` per group in the payment step only, run in `Promise.all` with the preview. `PreviewCheckout` carries `{ timeoutMs: 5000 }`; a failure raises to `error.tsx`.
- PDP: no new call; `estimated_delivery_at` rides on the existing `CalculateShippingFee(city, 0)` (`timeoutMs: 2000`, failure degrades to no date, never an error page).
- Pay page: at most one `CreatePayment` (only when no transaction) and one `ListBuyerOrders` (only when rendering the next-order link). Opening the same pay page twice never creates a second transaction (`CreatePayment` is idempotent per order).
- Place order keeps the double-submit lock and the Idempotency-Key; the attempt signature adds items, shop vouchers, platform voucher and `confirmed_address` fields so a changed input gets a new key.
- Money is int64 VND converted with `Number()`, no rounding, no client arithmetic over group figures.

## Data classification

| Field | Class | Purpose | Basis | Retention |
|---|---|---|---|---|
| `shipping_address` / `confirmed_address` (recipient, phone, street, ward, district, city) | personal | show the delivery address at confirm and bind the order to it | contract performance (the buyer's own address, already snapshotted on the order) | not stored by the frontend; rendered server-side for the owning buyer, sent back to team-order in the place-order action, never in the URL, a cookie, analytics (`trackEcommerce` receives none) or logs |
| Default address `city` on the PDP | personal (coarse location) | ETA and fee | contract necessity (as q5) | read per request; not stored; the PDP stays `force-dynamic` and per-user |
| `estimated_delivery_at` | transactional | delivery promise | contract necessity | owned by team-order; not stored here |
| Voucher codes in the URL (`sv`, `pv`) | not personal (a public promo code) | carry the buyer's choice across steps | contract necessity | URL only; no seller id other than the public shop id |
| Items selection (`items`) | not personal (cart line ids) | carry the selection across steps | contract necessity | URL only |

No new personal data is collected or persisted.

## Threat model

- Assets: the buyer's address, the charged amount, the per-order payment transactions.
- Abuse: (1) paying another buyer's order through `/checkout/pay/<id>`: the page calls `loadOrder` (principal-scoped `GetOrder`, PermissionDenied/NotFound → 404) before any `CreatePayment`, and `CreatePayment` itself checks the order buyer; (2) forging `confirmed_address`: it only triggers the server comparison, team-order places at its own copy of the address; (3) forging a displayed total: informational, team-order recomputes and charges server figures; (4) injecting another shop's voucher into a group: refused by team-order/promotion, shown as the voucher reason; (5) error text injection: fixed Vietnamese constants for the mapped branches; (6) another buyer's address leaking through a shared cache: pages are `force-dynamic` and read with the buyer's own token. (7) `CreatePayment` as a side effect of rendering the pay page (a GET; a link prefetch or a repeat visit can trigger it): accepted, because `CreatePayment` is idempotent per order and runs only after the principal-scoped `GetOrder` and a PENDING online-method check, so a repeat creates nothing new (reviewer-recommended answer, pending human confirmation). A payment created just before the order is cancelled cannot settle: `ProcessMockPayment` re-reads the order and refuses a CANCELLED one (M1, owned by payment-unpaid-cancel). (8) Legacy `voucher_code`: never sent; team-order treats it as the platform slot only (M5), so an old client cannot route a shop code.
- Authz rule: checkout and pay pages require the buyer's session (guests redirect to `/login`, unchanged); the pay page acts only on orders `GetOrder` returns for the caller; the next-order link lists only the caller's own orders.
