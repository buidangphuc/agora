## Context

See proposal.md. Today: `lib/products.ts` already loads listings through `gatewayClients()` and `toProductView`; `/products` renders them. `lib/shop.ts` (static `SHOP_PRODUCTS`, cart in the URL as `id:qty`, totals computed locally) and `lib/shop-delivery.ts` (name/address/phone validation, delivery data in a cookie) back the `/shop/*` screens. `lib/session.ts` reads a `session` cookie that nothing sets; `requireSession` redirects to `/`. `packages/api-client` exposes `search`, `cart`, `order`, `auth`, `session`, `address`, `publicProfile` and `analytics` clients (added earlier in this stack). The backend contract: `CartService` keeps the cart per user on the server; `CreateOrder` takes `address_id` (empty means the default address), optional `item_ids`, `payment_method` and vouchers; `PreviewCheckout` quotes without writing; `AddressService` holds saved addresses. Local backend stack and its quirks are in memory `reference-local-e2e-stack`; only the needed services are started.

## Goals / Non-Goals

**Goals:** every displayed value from a gateway API; gaps recorded, not worked around; a real sign-in; a verified end-to-end buying run against a real gateway.
**Non-Goals:** backend changes, vouchers, payment execution, seller or returns screens, password reset, native apps.

## Decisions

1. **One catalogue.** `/products` and `/products/[id]` stay the catalogue (already data-backed, restyled); `/shop` and `/shop/[id]` become redirects to them. Add-to-cart lives on the detail page as a server action calling `cart.addToCart`. `/shop/cart`, `/shop/checkout` and `/shop/confirmation` keep their paths so existing links work; renaming them is not worth the churn. Assumption recorded: this changes public routes, which is acceptable because the template has no external consumers.
2. **View models.** New `lib/` loaders (`cart.ts`, `checkout.ts`, `orders.ts`) mirror `lib/products.ts`: take clients, call one RPC, map proto messages to plain view objects (`CartView`, `QuoteView`, `OrderView`, `AddressView`), convert `ApiError` kinds the same way `loadProduct` does (`not_found` becomes `notFound()`, `unauthenticated` redirects to `/login`). Screens never see proto types. Money arrives as minor units and is formatted with the existing `formatPrice`; the app never sums.
3. **Auth.** `/login` and `/register` are server-action forms calling `auth.login` and `auth.register`; on success the access token is stored in the `session` cookie (httpOnly, sameSite lax, secure outside local, path `/`, max-age from the response when given) and the user is redirected to the page they came from (`next` restricted to same-origin paths). `logout` deletes the cookie. `requireSession` redirects to `/login?next=...` instead of `/`. The `(internal)` layout and the cart, checkout, confirmation and dashboard pages call it. Refresh: when the backend returns a refresh token it is stored in a second httpOnly cookie and `auth.refreshSession` is used once on `unauthenticated`; if the contract returns no refresh token this is a gap entry and an expired session simply sends the user back to `/login`.
4. **Checkout flow.** Step 1 shows the saved addresses as a choice plus a form to add one (`address.createAddress`); step 2 shows `PreviewCheckout` (per-seller groups, shipping, totals) and a payment-method select limited to what the contract's `PaymentMethod` enum offers; submit calls `order.createOrder`. Backend validation errors (`invalid`) are shown against the field when the error detail names one, otherwise as a form-level message; the screen never re-validates what the backend owns (the old local `validateDelivery` is deleted). Confirmation reads `order.getOrder(id)` where the id comes in the redirect URL; no personal data is placed in the URL.
5. **Dashboard** lists `order.listBuyerOrders` in a `Table`; status labels come from the enum names mapped to plain words in one `lib/order-status.ts` map, and an unmapped value is shown as received (a gap if frequent).
6. **Search.** The list page gets a GET search form; with a non-empty `q` it calls `search.searchListings` and maps hits to the same card view; with no `q` it lists via `ListListings`. If `SearchService` is not in the verification stack, the search path is covered by the fake-transport test only and recorded as unverified.
7. **Images.** `Listing.image_keys` are storage keys; the contract exposes no public URL for them on the listing, so cards keep the neutral placeholder and `docs/gaps.md` records "listing images: no public URL in the contract". No URL is guessed.
8. **Gap register.** `docs/gaps.md` is one table: id, screen, need, what the contract or service lacks, current behaviour in the template, owner service, date. Added rule in `frontend.md`: a missing capability is a row here plus an honest empty state, never invented data. The register is also linked from `docs/agents/project.md`.
9. **Tests.** Loaders and server actions are tested with the existing fake transport (`createGatewayClients` with a `fetch` stub) for success, `not_found`, `unauthenticated` and `invalid`; there are no static product or cart fixtures except stub gateway responses inside tests. A source scan test fails if `templates/app` (non-test files) contains `SHOP_PRODUCTS`, a price literal pattern such as `priceMinor:` outside generated code, or imports `lib/shop`.
10. **Real-gateway verification.** Start the minimum services (gateway plus identity, listing, order and what they need; search only if cheap) using the repo's local stack recipe, seed through the APIs (register a user, create a listing as a seller via `ListingService.CreateListing` if no seed exists), run the flow in the browser pane (register, browse, add to cart, address, preview, place order, confirmation, dashboard), record each step's result and every deviation as a gap or a bug, then stop the services. Credentials only through the repo's secrets index; test users are created through the public API with throwaway values and not written to files.
11. **Changesets.** `api-client` gets a minor changeset only if it gains exports; `app` is private and needs none.

## Risks / Trade-offs

- [Backend may not be runnable locally in reasonable time] → the minimal stack is tried first; if a required dependency cannot be started, the run records exactly where it stopped, which screens were verified and which only by fake transport. This is stated in the final report, not hidden.
- [Seller listing creation may need roles the test user lacks] → use the seeded or e2e fixtures from the local stack memory; otherwise record as a gap in verification, not as a template workaround.
- [Removing `/shop` breaks bookmarks] → redirects keep them working.
- [Backend errors may not name fields] → form-level message plus a gap entry asking for field-level detail.
- [Token cookie without refresh may expire mid-flow] → sends the user to `/login` with `next`; recorded.
