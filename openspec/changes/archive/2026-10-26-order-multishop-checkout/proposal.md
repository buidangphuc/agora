## Why

A buyer whose cart spans several shops sees one summary, but team-order charges per shop: `runCheckout` (`team-order/internal/service/order.go`) groups the cart by seller (`groupBySeller`), quotes `CalculateShippingFee(city, group.itemsSubtotal)` per group, and puts the single voucher on the first group only (`idx == 0`). The frontend adds the numbers up itself, so the shown total and the "free shipping" label differ from the placed orders (backlog Q11, `plans/pm-review-2026-10/buyer-journey.md` #2, #3). The locked initiative (`plans/q11-checkout-coherence/00-spec.md`, 2026-10-16) makes team-order the checkout quote authority: a new `OrderService.PreviewCheckout` that reserves nothing and `CreateOrder` share one pure quote function, so preview = charge by construction. This slice is the team-order side (plus the team-gateway forwarder): per-group quote, shop vouchers scoped to their group, one platform voucher computed once on the selection subtotal and split across groups, `checkout_id` linking the orders of one checkout, and the platform voucher lifecycle (commit on first paid order, release when every order of the checkout is cancelled unpaid). It uses the contract of `q11-checkout-contract`, the voucher scope echo of `promotion-voucher-scope`, and the address resolver and ETA of `order-address-eta`. The checkout UI is `frontend-checkout-coherence`.

initiative: q11-checkout-coherence

## What Changes

- **team-order, quote** (`internal/service/checkoutquote.go`, new): a pure function `quoteCheckout(groups, city, now, shopDiscounts, platformDiscount)` that returns per group `items_subtotal`, `shipping_fee`, `is_free_shipping`, `shop_discount_amount`, `platform_discount_amount`, `total_amount` and `estimated_delivery_at`, and the summed totals. `shipping_fee` = `CalculateShippingFee(city, group.items_subtotal)` per group (threshold per group, never on the selection). Platform discount proration: group share = `D * group.items_subtotal / selection_subtotal` (int64 integer division), remainder `D - sum(shares)` to the group with the largest `items_subtotal`, ties to the lowest `seller_id`. Group total = `items_subtotal + shipping_fee - shop_discount - platform_share`, clamped at 0. `runCheckout` and `PreviewCheckout` both call it; nothing else computes a figure.
- **team-order, PreviewCheckout** (`internal/service/order.go`, `internal/handler/order.go`): new RPC for a USER principal. It loads the caller's cart, selects `item_ids` (empty = whole cart), runs the self-purchase check and the q5 price pre-check (`precheckPrices`, which re-prices the buyer's own cart lines and returns "price changed", the only write), resolves the address with the resolver of `order-address-eta` (no saved address at all -> `shipping_quoted=false`; unknown `address_id`, or addresses with none default and an empty `address_id` -> `FAILED_PRECONDITION` "address not found", no first-address fallback; identity unreachable -> `UNAVAILABLE`), groups by seller, validates each voucher with `ValidateAndReserve` under reservation ids `preview:<buyer id>:<random>` as team-order's service principal, releases those holds right after quoting (best effort, never committed), calls `quoteCheckout`, and returns groups sorted by seller id, per-voucher `VoucherQuote` (valid or the reason), the totals and `shipping_address`. It reserves no stock, no flash stock, creates no saga and no order.
- **team-order, voucher routing** (`internal/service/redemption.go`, `checkoutquote.go`): `CreateOrder` and `PreviewCheckout` accept `shop_vouchers` (one per `seller_id`), `platform_voucher_code` and the legacy `voucher_code`. Shop voucher: one `ValidateAndReserve` on its group (`seller_id` = that group, `cart_subtotal` = group `items_subtotal`, reservation id = that group's order id, as today). Platform voucher: one `ValidateAndReserve` with empty `seller_id`, `cart_subtotal` = selection subtotal, reservation id `platform:<checkout_id>`; its `min_spend` is therefore checked once on the whole selection. The response `scope` / `seller_id` (from `promotion-voucher-scope`) are verified: a PLATFORM-scope code in a shop slot, a SHOP-scope code in the platform slot, or a SHOP voucher echoing a seller other than the slot's, is refused. Legacy `voucher_code` is the platform-voucher slot only (M5): it is validated exactly like `platform_voucher_code`, with no SHOP auto-routing and no probe; a SHOP echo (any seller) or an unknown code is refused like any platform-slot refusal (preview `valid=false`, `CreateOrder` `FAILED_PRECONDITION`). A legacy client that sends a shop code in `voucher_code` is therefore refused where today it discounted the first group (the frontend stops sending `voucher_code` in `frontend-checkout-coherence`). The response `scope` from promotion is mapped to the local `CheckoutVoucherScope` enum of `order.proto` for `VoucherQuote.scope` (C8; same numbers, no `promotion.proto` import in order.proto). Without a promotion client all vouchers are ignored at `CreateOrder` (as today); preview reports them `valid=false` with the reason "vouchers unavailable".
- **team-order, checkout** (`order.go`, `saga.go`): `runCheckout` places one order per group at the quoted figures; each order stores `checkout_id` (= saga id), its own `voucher_code` / shop `discount`, `platform_voucher_code` and `platform_discount_amount`; `Order.discount_amount` = shop discount + platform share. `failAndCompensate` releases every voucher hold of the attempt (each shop hold under its order id, the platform hold under `platform:<checkout_id>`), not only the first group's.
- **team-order, persistence** (`internal/repository/order.go`, `migrations/`): new columns `checkout_id`, `platform_voucher_code`, `platform_discount_amount` on `orders` (next free migration number at build time; defaults '' / 0, so legacy orders are unchanged), an index on `checkout_id`, and `OrderRepository.ListOrdersByCheckout(ctx, checkoutID)` in Postgres and in memory. The handler maps the three fields to `Order`.
- **team-order, platform voucher lifecycle** (`internal/consumer/payment.go`, `internal/service/order.go`): on settle of an order with a `platform_voucher_code`, the consumer calls `CommitReservation("platform:<checkout_id>")` (idempotent in promotion, so "counted used on the first paid order" holds for any later one). `releasePlatformVoucherIfCheckoutCancelled(ctx, order)` runs after every cancel claim (buyer `CancelOrder` and the system cancel of q10's unpaid-order expiry sweeper, which calls the same helper): when every order of the `checkout_id` is Cancelled and none has `paid_at`, it calls `ReleaseReservation("platform:<checkout_id>")`; otherwise nothing is released and no sibling is re-priced. A release error is logged and never fails the cancel.
- **team-order, handler errors** (same in `PreviewCheckout` and `CreateOrder`): duplicate `seller_id` in `shop_vouchers`, one code named twice, or `voucher_code` together with `platform_voucher_code` -> `INVALID_ARGUMENT` before any promotion call; in `CreateOrder` a refused voucher -> `FAILED_PRECONDITION` with the reason (`ErrVoucherRejected`); promotion transport error -> `UNAVAILABLE` (`ErrPromotionUnavailable`).
- **team-gateway** (`internal/edge/order.go`): `OrderForwarder.PreviewCheckout` forwarding through `callRead` with the caller's principal, exactly like `CalculateShippingFee`; the `team-gateway/proto` copy is refreshed from `platform-core/packages/proto` (never hand-edited) and stubs regenerated.
- **Proto copies**: `team-order/proto` refreshed from `platform-core/packages/proto` (contract slice version), stubs regenerated.
- **platform-e2e** (owned by this slice): `features/order/multishop_checkout.feature` and steps, shop and platform voucher helpers in `support/` (seeded through `VoucherService.CreateVoucher`).
- **Docs**: `platform-core/docs/ROADMAP.md` promotion note ("platform campaigns at checkout, first seller group only") updated; `team-order/README.md` documents the routing and lifecycle.
- Not changed: team-payment, team-promotion (scope echo is `promotion-voucher-scope`), stock/flash hold logic, the frontend, shipping-method choice.

## NFR

- Latency: `PreviewCheckout` p95 <= 300 ms on the local stack for <= 5 groups. Calls: one `GetCart`, one `ListAddresses`, the q5 read-only price pre-check (`GetListing` per line, `GetActiveFlashSale` per distinct listing), one `ValidateAndReserve` and one best-effort `ReleaseReservation` per applied voucher (voucher calls run concurrently per voucher); no stock reservation and no flash hold call. `CreateOrder` adds at most one `ValidateAndReserve` per extra voucher (a legacy `voucher_code` costs the same single call as `platform_voucher_code`). Each upstream call keeps the existing `UPSTREAM_CALL_TIMEOUT_SECONDS` bound (default 2 s), no retries.
- Availability: promotion unset -> vouchers ignored at `CreateOrder` (today) and reported invalid in preview; promotion outage -> `UNAVAILABLE` in both, nothing held; an identity outage fails `PreviewCheckout` `UNAVAILABLE` and never places an order (`order-address-eta`).
- Limits: int64 VND, integer division only; for every checkout the sum of group totals = response total = sum of placed `total_amount`; at most one shop voucher per seller and one platform voucher per checkout.

## Data classification

| Field | Class | Purpose | Basis | Retention |
|---|---|---|---|---|
| `shipping_address` in the preview response | personal (recipient name, phone, street, ward, district, city) | show the buyer which address the quote used; sent back as `confirmed_address` | contract performance (order delivery) | not stored by preview; returned only to the owning user; never logged (log address ids only) |
| `checkout_id`, `platform_voucher_code`, `platform_discount_amount` on the order | operational, pseudonymous | link sibling orders, route platform voucher commit and release, show the discount | contract performance | with the order row (existing order retention) |
| voucher codes and `buyer_id` sent to promotion | pseudonymous | validate and hold a discount | contract performance | held in promotion until commit, release or its expiry; preview holds are released immediately |
| preview reservation id `preview:<buyer id>:<random>` | operational | isolate preview holds from real ones | same | released right after the quote |

No new personal-data collection.

## Threat model

- **Assets:** the charged amount of every order, voucher quota and discount money, the buyer's address, the promotion service credential (`service-team-order`, scope `promotion.reserve`).
- **Abuse cases:**
  - Another buyer's cart or address previewed: `PreviewCheckout` reads only the cart and addresses of the principal's own id (no buyer id in the request).
  - Shop voucher of shop A used on shop B's group, or a platform code in a shop slot to skip a per-shop rule (and the reverse): promotion checks the seller, team-order checks the echoed scope and seller; either refuses.
  - Splitting a selection to dodge the platform `min_spend` or to double a discount: `min_spend` is checked once on the whole selection; the discount is computed once and split, so shares always sum to it.
  - Stacking shop and platform vouchers to get a negative total: the group total clamps at 0.
  - Cancel all orders but one and keep the platform discount on a smaller order: shares are fixed at placement; nothing is re-priced.
  - Quota drained by repeated previews: preview holds use their own namespace and are released at once; commit happens only in the settle consumer.
  - A user token committing or releasing a platform hold: the hold RPCs stay service-only in promotion; team-order calls them as its service principal.
  - Platform voucher released while an order is paid: the release runs only when no order of the checkout has `paid_at`; a committed hold cannot be released in promotion.
- **Authz rule:** `PreviewCheckout` and `CreateOrder` require a USER principal (`PERMISSION_DENIED` otherwise, `UNAUTHENTICATED` without one) and act only on the principal's own cart; `GetOrder` / `CancelOrder` authz is unchanged.
