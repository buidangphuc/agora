# Design

## Decisions
- One consumer per owning repo, each with its own group and `identity.events.<svc>.dlq`, mirroring `team-domain/internal/events/identity.go`. team-analytics (Go, `consume` package of go-sdk), platform-recsys (Python, `confluent-kafka`, as `recsys.nearline`), team-ai (Python, `aiokafka`, as the listing indexer addon). Group and DLQ names: `team-analytics.user-erasure` / `identity.events.analytics.dlq`; `platform-recsys.erasure` / `identity.events.recsys.dlq`; `team-ai.user-erasure` / `identity.events.team-ai.dlq`. The topic also carries `UserStatusChanged`; envelopes of any other type are skipped silently (not DLQ'd), an undecodable envelope or a `UserErased` with an empty `user_id` goes to the DLQ.
- Re-key, not delete, in the warehouse: a pseudonym `erased:<32 hex>` from `crypto/rand`, generated per erasure and never persisted next to the user id. This keeps funnels, revenue and distinct-visitor counts stable while removing the link to the person. Favourite and follow facts are deleted because they are personal preferences with no aggregate value once the user is gone. Rows where the user is the *seller* (`order_facts.seller_id`, `engagement_facts.seller_id`, `listing_sellers.seller_id`) are re-keyed to the same pseudonym.
- Columns re-keyed in `tracking_events` for rows with `principal_type='user' AND principal_id=<user>`: `principal_id`, `session_id`, `anonymous_id` to the pseudonym; `ga_client_id` and `properties` set to NULL (device id, free-form). Anonymous rows sharing one of the user's `anonymous_id` values are re-keyed too (`anonymous_id` -> pseudonym, `ga_client_id` -> NULL) because `tracking_events_resolved` stitches them to the user. `search_query` stays (aggregate value, no id).
- Tombstone `erased_users(user_hmac PRIMARY KEY, pseudonym, erased_at)`: `user_hmac = HMAC-SHA256(user_id, ERASURE_TOMBSTONE_SECRET)`. The writers of `tracking_events`, `order_facts` and `engagement_facts` look up the HMACs of the batch's distinct user ids inside the insert transaction and write the pseudonym instead. Lookup inside the same transaction closes the race between a buffered batch and the purge (DuckDB serialises writers).
- Idempotency: the purge is one transaction; a redelivery finds no rows and an existing tombstone and is a no-op that still commits the offset.
- Parquet export is not changed; it already rewrites all files each cycle from the tables, so clean tables give clean files. The recsys dataset `als_interactions` and the featurestore snapshots are derived from those files.
- Pseudonymised keys must not become features: featurestore input views `events`, `facts`, `orders` exclude rows whose `user_key`, `user_id` or `buyer_id` starts with `erased:`. Done at the input layer, so `registry/sql/*` and `registry/features.lock` hashes do not change and no feature view version bumps.
- Featurestore has no Kafka client and the initiative forbids new dependencies beyond MinIO in verification. Therefore featurestore erasure is state-based: `materialize` deletes, for the user-keyed views `user_activity` and `user_preferences`, every online key `fs:<view>:v<ver>:<entity>` whose entity is not in the new snapshot (SCAN, then DEL in chunks), after writing the new rows and before the `current`/`meta` pointers. Recsys deletes its own Redis keys itself; recsys never touches DB 2.
- recsys Redis deletions: `recs:v1:gen:*:user:<id>` (SCAN with the escaped id), `recs:v1:user:<id>`, `recs:nearline:user:<id>:items`, `recs:nearline:user:<id>:cats`. Qdrant: delete by filter `user_key == <id>` in every collection matching `user_als_vectors__*` (the alias is not a collection). Session keys `recs:nearline:session:<sid>:items` are keyed by anonymous session ids, not user ids, and expire in 24 h; not touched.
- team-ai deletions: `chat:session:<quote(id)>:*`, and every key under `QUOTA_REDIS_PREFIX` and `RATE_LIMIT_REDIS_PREFIX:principal` that embeds the user principal (`user:<id>`), found with SCAN. team-ai's cached `recs:v1:gen:*:user:<id>` are recsys-owned and handled by recsys.
- BigQuery adapter: out of scope (write-only, prod, local-first). The erasure consumer is wired only for `WAREHOUSE_DRIVER=duckdb`, like the engagement consumer; with `bigquery` it is not started and a warning is logged. This gap is listed in the hand-off open issues.

## Config (team-analytics, `.env.example` kept in sync)
`IDENTITY_EVENTS_TOPIC` (default `identity.events`), `ERASURE_CONSUMER_GROUP` (default `team-analytics.user-erasure`), `ERASURE_DLQ_TOPIC` (default `identity.events.analytics.dlq`), `ERASURE_TOMBSTONE_SECRET` (local default for local/test, required when ENV is staging or prod). None may be empty.

## Test seams
Go: a fake DuckDB (real in-process DuckDB, no mock service) seeded with rows through the real writer, and the Kafka test harness already used by `internal/app/kafka_test.go`. Python: fakeredis and the Qdrant in-memory client already used by the repos' tests, plus the repos' fake Kafka source (`RecordSource`, `poll/commit` doubles).
