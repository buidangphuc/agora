## Why

team-analytics is the last data-plane Go service still on its own copy of the platform layer: its config binder, `.env.example` drift check, slog builder, gRPC health server, principal interceptor, hand-written franz-go consumer loops and signal handling are copies of what `platform-core/packages/go-sdk` v1.0.2 now provides (ADR-0016). The copies differ from the rest of the platform in ways that already hurt:

- Consumers log the raw Kafka record key (`slog.String("key", string(rec.Key))` in `internal/consumer`). The key is a user, session or seller id, which is personal data. The SDK consumers log a keyed `key_fp` instead.
- A record that cannot be written is retried in a hand-written loop with no attempt limit and no dead-letter topic for the tracking, order and listing streams. A poison write blocks the group forever.
- Health is a constant SERVING; a liveness probe cannot be told apart from readiness, so a DuckDB outage cannot be shown without risking a restart loop.
- `KAFKA_ENABLED=false` is a boot error for the consumer, `GRPC_REFLECTION_ENABLED` defaults to true, and `GA4_EXPORT_SOURCE=fixture` is a data-source switch that can be set in any environment. User rules of 2026-10-22/23: no dependency enable flags, no runtime fallbacks, mock data only through `pkg/mockdata`, never in a strict ENV.
- The GA4 relay serves hand-written HTTP `/healthz` and `/readyz` and runs its own consume, commit and dead-letter code.

`plans/go-sdk-migration/PLAN.md` names SDK v1.0.1 as the adopted version; this change targets v1.0.2 (tag on origin) because it supersedes the plan: the settled Clarifications fix v1.0.2, so the plan's version is outdated.

Source: `plans/go-sdk-migration/PLAN.md`, `platform-core/docs/ADR/0016-go-service-convention-and-sdk.md`, `openspec/specs/go-platform-sdk`. Branch base: `feat/go-sdk-all` = origin/main + C4 q6 disputes + q11 checkout. Main's behaviour wins over the earlier attempt on `origin/feat/go-sdk-v1-e2e`, which is a reference only.

initiative: go-sdk-migration

## What Changes

- **Module and tooling.** `go.mod` requires `github.com/buidangphuc/agora/platform-core/packages/go-sdk v1.0.2` (no `replace`, no `third_party`). The `Makefile` includes `../platform-core/make/go-service.mk` and sets `LINT_CONFIG := ../platform-core/packages/go-sdk/.golangci.yml`; `golangci-lint` is pinned as a `tool` directive like the SDK `go.mod`. No doc comments are added (the shared revive rules do not require them).
- **Layout (ADR-0016).** `cmd/consumer`, `cmd/ga4-relay`, `cmd/ga4import` each shrink to `main.go` calling `internal/app`. New or renamed packages: `internal/app` (composition roots `RunConsumer`, `RunGA4Relay`), `internal/config` (SDK groups), `internal/rpc` (AnalyticsQueryService handlers: authorize, call the repository, map the error), `internal/events` (renamed from `internal/consumer`), `internal/ga4import` (importer, scheduler, trigger handler and CLI moved out of `cmd/`). Removed: `internal/bootstrap`, `internal/grpcserver`, `internal/interceptor`, `internal/observability/logging.go`, `internal/consumer/batcher.go`. `internal/query` keeps the repository and aggregations; `internal/warehouse` keeps the writer seam and the DuckDB and BigQuery adapters.
- **Config.** `Settings` embeds `config.Runtime` and `config.GRPC` and names `OTel`, `Kafka`, `LogKeyFP`, `MockData` plus the service groups (warehouse, batch, tracking, recs, engagement, GA4, metrics). `ENV` becomes required, `SHUTDOWN_GRACE_SECONDS` becomes `SHUTDOWN_GRACE` (Go duration) plus `SHUTDOWN_DRAIN_DELAY`, `KAFKA_BROKERS` and `LOG_KEY_FP_SECRET` are required in a strict ENV. `GA4_API_SECRET`, `GA4_MEASUREMENT_ID` and `GA4_EXPORT_DATASET` are required in a strict ENV. **BREAKING** (accepted): `KAFKA_ENABLED`, `SHUTDOWN_GRACE_SECONDS`, `GA4_EXPORT_SOURCE`, `GA4_RELAY_PROBE_PORT` are removed; `OTEL_SERVICE_NAME` stays an accepted key (SDK OTel group); `GRPC_REFLECTION_ENABLED` defaults to false and is refused in a strict ENV. New keys: `KAFKA_DLQ_TOPIC` (default `analytics.events.dlq`), `KAFKA_LISTING_DLQ_TOPIC` (default `listing.events.analytics.dlq`), `LOG_KEY_FP_SECRET`, `MOCK_DATA`, `GA4_IMPORT_TRIGGER_URL`.
- **No fallbacks.** Every `Enabled` flag and in-memory implementation that a binary can reach is deleted: `query.MemoryRepository`, `ga4relay.NewMemoryLedger`, `ga4relay.NewMemoryMappingStore` move to test files; `warehouse/fake` stays as a test fake imported only from tests.
- **Mock data.** The only existing mock switch, `GA4_EXPORT_SOURCE=fixture`, becomes `MOCK_DATA=ga4export`; the real importer, `ga4_sessions` replace and reconcile path run on Parquet fixtures from `GA4_EXPORT_FIXTURE_DIR`.
- **Consumers on `pkg/kafkax` and `pkg/consume`.** The tracking and order consumer becomes a `consume.BatchConsumer` (batch size = `BATCH_MAX_SIZE`, max wait = `BATCH_FLUSH_INTERVAL_SECONDS`; its dead-letter producer blanks `ga_client_id` without analytics consent), the listing consumer a `consume.BatchConsumer` from the earliest offset, the engagement consumer a `consume.Consumer`. Consumer group names are unchanged. Handlers log `key_fp`, never the key.
- **gRPC, auth, errors, health, lifecycle.** `grpcx.NewServer` replaces `internal/grpcserver`; `auth.RequirePrincipal` and `auth.RequireScopes` replace `internal/interceptor`; `grpcx.Status` with an error table maps repository errors (unknown errors become `internal error`); `healthx` serves overall readiness (DuckDB ping only; Kafka is not a readiness check) and an independent `liveness` service; `lifecycle.Run` with `StopAfter(server, workers...)` replaces signal and goroutine code; `logx` and `otelx` replace the logger and tracer set-up.
- **GA4 relay.** Serves gRPC health only (replaces HTTP `/healthz` and `/readyz`); consumes through `consume.Consumer`; `Relay.Handle` returns `consume.Permanent` for dead-letter cases so the SDK dead-letters and commits; the in-code `DLQProducer`, `OffsetCommitter` and `Message` types are removed. The relay's own exact retry schedule (1 s doubling, cap 30 s, 5 attempts) stays in `ga4relay.Client` (see design D7).
- **Spec deltas.** ADDED capability `analytics-service-runtime`. MODIFIED in `ga4-export-import`: "The daily GA4 import builds ga4_sessions idempotently", "The import runs inside the consumer process", "The import is deployed with disabled-by-default configuration" (the `GA4_EXPORT_SOURCE` switch and the fixture-directory gate). MODIFIED in `ga4-purchase-relay`: "Disabled without secret" (disabled only in a local or test ENV; a strict ENV refuses to boot without credentials) and "No inbound surface and restricted order.events writers" (HTTP probes become gRPC health) and "Retry and failure handling" (store failures beyond 5 attempts are dead-lettered and counted). MODIFIED in `analytics-review-hidden`: "The engagement consumer records a review_hidden fact" (the corrupt-payload scenario now describes SDK dead-lettering with `dlq-*` headers). MODIFIED in `tracking`: "Events are written in batches for throughput" (offsets also move after a batch is parked on the dead-letter topic, with `ga_client_id` blanked without consent). MODIFIED in `ga4-export-import` also: the empty-dataset no-op applies in a local or test ENV only. Other specs' `VERIFIED BY` paths that point at moved packages are repointed by task 1.9. Switches kept on purpose and not dependency flags: `PARQUET_EXPORT_INTERVAL_SECONDS=0` (turns the optional Parquet export off), an empty `METRICS_ADDR` (no metrics listener), an empty `GA4_EXPORT_DATASET` (import no-op), relay credentials unset (relay disabled); none substitutes an in-memory or noop dependency.
- **Deploy track (not done here).** Compose and gitops edits (strict ENV overlays for the raw manifests, `GRPC_REFLECTION_ENABLED=true` in local compose, the service bullet of the shared requirement "Services refuse unsafe configuration in staging and production", which only change deploy-go-sdk-v1 modifies) are listed in `tasks.md` under "Deploy track (done by change deploy-go-sdk-v1)". `LOG_KEY_FP_SECRET` in Vault is a human task. No migrations: team-analytics has no Postgres.

## NFR

- Ingest throughput: at least 100 tracking events/s sustained, unchanged (`openspec/specs/tracking`). Offsets move after a durable warehouse write or after the batch is parked on `KAFKA_DLQ_TOPIC` following 5 failed attempts (at-least-once is no longer unconditional). A transient warehouse outage longer than the 4 backoff waits (about 1.5 s) dead-letters whole batches; recovery is a replay of the dead-letter topic (design D5), a runbook step of the deploy change. The same limit applies to the GA4 relay's ledger and mapping store (design D7).
- Rebalance budget of the other consumers: the GA4 relay sets `MaxPollRecords = 1` because one record can block 15 s (40 s if GA4 hangs) inside `Client.Send` during a GA4 outage, so `MaxPollRecords x 40 s` stays under the 60 s rebalance timeout (`TestRelayConsumerOptionsFitRebalanceBudget`); the engagement consumer sets `MaxPollRecords = 10`, `10 x (1.5 s + 5 x 50 ms)` = 17.5 s under 30 s (`TestEngagementOptionsFitRebalanceBudget`); the tracking batch is `TestMaxSizeBatchWriteFitsRebalanceBudget`. Ingest throughput after the move to `BatchConsumer` is proven by `TestBurstOf1000EventsIsWrittenAtOrAbove100PerSecond`.
- Partial-batch bound: a fetch returns after at most `BATCH_FLUSH_INTERVAL_SECONDS` (default 2 s) and carries at most `BATCH_MAX_SIZE` (default 500) records.
- Poison write: a batch whose write fails is attempted 5 times with SDK backoff (100 ms base doubling, 30 s cap), then dead-lettered and committed, so one bad batch blocks its group for at most 4 backoff waits (100 ms, 200 ms, 400 ms, 800 ms) plus 5 handler runs instead of forever. One batch at `BATCH_MAX_SIZE` (500) must finish handling, attempts included, inside the group rebalance timeout (franz-go default 60 s): a DuckDB write of 500 rows takes under 5 s, so 5 attempts plus about 1.5 s of waits stay under 27 s, checked by `TestMaxSizeBatchWriteFitsRebalanceBudget`.
- Health: `liveness` answers from memory (no I/O); readiness flips to NOT_SERVING within one health interval plus 1 s (`healthx.DefaultInterval` is 5 s; tests inject a short interval) of a DuckDB ping failure; a Kafka outage does not change readiness.
- Shutdown: health drains first, then the server stops within `SHUTDOWN_GRACE` (default 10 s), then the consumers stop and flush a final batch, then DuckDB closes.
- Read RPC latency, GA4 import budget (5M rows in 10 min), reconcile thresholds and relay latency budget: unchanged.
- Availability: single replica with `Recreate` strategy (DuckDB file lock) is unchanged.

## Data classification

| Field | Where | Purpose | Basis | Retention |
|---|---|---|---|---|
| Kafka record key (user, session or seller id) | in memory in consumers; only its `key_fp` is logged | correlate a failing record across log lines without exposing the id | legitimate interest | log line: platform log retention; the raw key is never logged |
| `key_fp` (first 12 hex of HMAC-SHA-256 with `LOG_KEY_FP_SECRET`) | logs | as above; not reversible without the secret | legitimate interest | platform log retention |
| `LOG_KEY_FP_SECRET` | env / secret store | keys the fingerprint | n/a (secret) | never logged, never in errors; strict ENV requires it |
| Original record (user id, session id, listing id, amounts) copied to `KAFKA_DLQ_TOPIC`, `KAFKA_LISTING_DLQ_TOPIC`, `ENGAGEMENT_DLQ_TOPIC`, `GA4_RELAY_DLQ_TOPIC` | Redpanda dead-letter topics | park a record the warehouse cannot take, for repair or replay | legitimate interest | topics created with `retention.ms=604800000` (7 days), as `analytics.ga4-relay.dlq` already is |
| `ga_client_id` of a tracking record | dead-letter copy on `KAFKA_DLQ_TOPIC` and `GA4_RELAY_DLQ_TOPIC` | none without consent: blanked by the redacting DLQ producer before publish when `consent.analytics` is false, absent or version-0; kept only for a consented record so a replay is lossless | consent `analytics` | 7 days, same topics |
| Tracking, order, engagement and listing rows in the warehouse | DuckDB / BigQuery | unchanged by this change | unchanged (consent gates in `openspec/specs/consent`) | unchanged |
| GA4 relay mapping (buyer id to GA client id) and sent-order ledger | relay DuckDB file | unchanged | consent `analytics`, unchanged | unchanged (mapping expires, ledger purged hourly) |
| `GA4_API_SECRET` | secret store | GA4 Measurement Protocol | n/a (secret) | never logged, unchanged |

No new personal field is stored. No DPO sign-off is requested (user rule): basis is legitimate interest and retention is the platform log retention.

## Threat model

- Assets: the warehouse (behavioural and order data), seller revenue figures served by `AnalyticsQueryService`, dead-letter topics holding original records, `LOG_KEY_FP_SECRET`, `GA4_API_SECRET`, the gRPC surface description.
- Abuse 1, raw user ids in logs (today: raw `rec.Key`). Control: handlers and the SDK consumers log `key_fp` only; a test captures all log output for a record keyed `user-123` and asserts the string is absent.
- Abuse 2, mock data in a deployed environment. Control: `config.Load` refuses a non-empty `MOCK_DATA` in a strict ENV before any other validation; the real importer always runs.
- Abuse 3, reflection left on. Control: default off; refused in a strict ENV.
- Abuse 4, a seller reads another seller's analytics or a non-admin reads admin RPCs. Control: `auth.RequireScopes`/`RequirePrincipal` in each handler; `admin` is a scope matched exactly, never a wildcard; the seller rule (own id or `admin`) is unchanged and enforced in team-analytics, not at the gateway.
- Abuse 5, a forged `OrderPaidEvent` triggers a GA4 purchase. Control unchanged: broker ACL on `order.events`; the relay serves no inbound endpoint except gRPC health.
- Abuse 6, a poison record blocks ingestion or is lost. Control: SDK attempt limit, then dead-letter and commit; undecodable tracking records are counted in `decode_failures` and skipped as today.
- Abuse 7, a dependency outage restarts all pods. Control: `liveness` health service independent of DuckDB; Kafka is not in readiness at all; probes opt in through the deploy track.
- Abuse 8, a parked record leaks a GA client id the visitor did not consent to share. Control: the redacting DLQ producer blanks `ga_client_id` on every tracking record published to `KAFKA_DLQ_TOPIC` or `GA4_RELAY_DLQ_TOPIC` when consent is not granted; a test reads the topic back.
- Authz rule: `AnalyticsQueryService` seller RPCs allow an authenticated user whose id equals `seller_id`, or a principal holding the exact `admin` scope; admin RPCs require `admin`; health needs no principal; the relay has no business RPC.
