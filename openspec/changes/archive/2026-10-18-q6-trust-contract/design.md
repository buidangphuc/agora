# Design

## Clarifications
### Round 1 — 2026-10-16
- Field names and numbers follow the Contracts section of `plans/q6-trust-enforcement/00-spec.md` verbatim (locked). The initiative leaves error codes and reason-code lists to this slice; they are fixed here and written into the proto comments.
- Reason codes: listing moderation `prohibited_item | counterfeit | misleading | inappropriate | duplicate | seller_enforcement | other`; report `prohibited_item | counterfeit | scam | misleading | inappropriate | other`; user status: any non-empty lower_snake_case code of at most 64 chars (the admin UI offers a fixed list; the server does not enumerate it). All are string fields, not enums, so the lists can grow without a wire change. Notes are at most 500 characters after trim.
- Moderation transitions (documented on `ModerateListing`): APPROVE only from PENDING_REVIEW; REJECT and BAN from PENDING_REVIEW or PUBLISHED (a report on a live listing must be actionable); every decision on DRAFT, HELD, REJECTED or BANNED is FAILED_PRECONDITION. `HELD` is entered and left only by the enforcement consumer, never by an RPC.
- `Listing.status` on `CreateListing`/`UpdateListing` is documented as a request: DRAFT stores a draft, PUBLISHED asks for publication, every other value is ignored; an unset `status` on `UpdateListing` keeps the stored status (it is not a DRAFT request); the stored status is server-derived. The `moderation` field is ignored on writes.
- `SetUserStatus`: setting the current status again is allowed (it can change reason or `until`) and emits again; RESTRICTED, SUSPENDED and BANNED revoke every session (also on a re-set), ACTIVE revokes none. `until` must be in the future for SUSPENDED and unset otherwise.
- `CreateReport` on an own listing: engagement resolves the listing owner from its own seller-listings projection; an unknown owner does not block the report. Refusal code is FAILED_PRECONDITION.
- `CreateDispute` with `return_id`: the defendant is the order's seller; a supplied `defendant_id` that differs is INVALID_ARGUMENT; the claimant must be the order's buyer.
- `ResolveDispute.ruling` is allowed only with `status` RESOLVED; a ruling with any other status is INVALID_ARGUMENT (matches engagement-dispute-escalation). `DisputeResolved` is emitted for every dispute reaching RESOLVED or REJECTED (`return_id` empty when not linked, ruling UNSPECIFIED when not given).
- Audit catalogue: the comment lists 17 actions; `return.dispute_refund` is written by team-order as a system action with the resolving admin as actor.
- `events.proto` imports `google/protobuf/timestamp.proto` (for `resolved_at`) and `engagement.proto` (same package) for `DisputeStatus` and `DisputeRuling`; every consumer copy of `events.proto` therefore also carries `engagement.proto`.
- Copies: listed in the proposal. Several current copies are stale subsets (for example team-domain and team-order `identity.proto`); they are replaced by the full source, which is additive for those consumers. `team-analytics` gets the full `engagement.proto` because its `events.proto` copy needs it.
- Tests: one dynamic-descriptor test per touched package (same approach as `flashstock_compat_test.go`, reading `buf build -o -#format=json`), stdlib only; the audit catalogue test is extended in place.
- q10 boundary: q10 does not touch `engagement.proto`, so this slice owns the dispute field numbers 11, 12 (Dispute), 5 (CreateDisputeRequest) and 4 (ResolveDisputeRequest). q10 keeps `OrderReturn.can_escalate`, Order fields 18-24 and the return-window fields; this slice adds none of them.
- A8 [behaviour] Trust contract: Seller cannot set server-owned fields: is every seller content edit of a PUBLISHED listing re-screened, and is an unset status distinct from DRAFT? → **Yes; a flagged edit moves it to PENDING_REVIEW; an unset status on UpdateListing keeps the stored status** (human)
- A9 [behaviour] Trust contract: Moderation errors and transitions are documented: from which statuses may an admin REJECT/BAN, and can APPROVE reverse REJECTED/BANNED? → **REJECT/BAN from PENDING_REVIEW and PUBLISHED; APPROVE only from PENDING_REVIEW; DRAFT, HELD, REJECTED, BANNED refuse every decision** (human)
- A10 [errors] Trust contract: Seller cannot set server-owned fields: may a seller delete a BANNED or HELD listing? → **No, FAILED_PRECONDITION** (human)
- A11 [privacy] Trust contract: Status is documented as server-owned: who sees `screen_flags`? → **Admin only; the owner sees reason_code and note only** (human)
- A12 [authz] Trust contract: Seller cannot set server-owned fields: does an admin's own listing skip the screen? → **No, it follows the seller path and is still audited** (human)
- A13 [privacy] Trust contract: Moderation errors and transitions are documented: do ListingChanged events carry the moderation note or screen flags? → **Neither** (human)
- A14 [behaviour] Trust contract: SetUserStatus authz, audit and errors are documented: which statuses revoke sessions? → **RESTRICTED, SUSPENDED, BANNED (also on a re-set) revoke all sessions; ACTIVE revokes none** (human)
- A15 [behaviour] Trust contract: Event and login refusal are documented: when is an expired suspension lifted? → **At the user's next Login only; RefreshSession never lifts; a sweeper is a follow-up** (human)
- A16 [privacy] Trust contract: Event and login refusal are documented: does the login refusal tell suspended from banned or show an end time? → **No, one generic message ("tài khoản bị khóa")** (human)
- A17 [behaviour] Trust contract: Dispute state machine is documented: which transitions are allowed and what happens to a ruling with a non-RESOLVED status? → **OPEN→INVESTIGATING|REJECTED; INVESTIGATING→INVESTIGATING (note update)|RESOLVED|REJECTED; a ruling with any status but RESOLVED is INVALID_ARGUMENT** (human)
- A18 [authz] Trust contract: Dispute listing authz is documented: may a return be re-escalated after its dispute closed, and who reads ListOrderDisputes? → **Re-escalation allowed while can_escalate is true; ListOrderDisputes for the order's buyer, seller or an admin** (human)
- A19 [errors] Trust contract: CreateReport rules are documented: is there a cap on open reports, and is the resolution note required? → **Max 20 OPEN reports per reporter (RESOURCE_EXHAUSTED); resolution_note required, 1-500 chars** (human)
- X1 [contract] Trust contract: Dispute fields have fixed numbers: must the dispute field numbers be agreed with q10? → **No; q10 no longer touches engagement.proto, this slice owns them** (human)
- X2 [behaviour] Trust contract: ScreenListing is documented as internal: what does the mock backend return for clean text? → **ALLOW, so existing e2e seeds still auto-publish** (human)
