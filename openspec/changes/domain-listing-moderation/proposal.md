## Why

Any seller can publish a listing, or undo an admin's rejection, by sending `status=PUBLISHED` on `CreateListing` / `UpdateListing`: team-domain `handler/listing.go` `fromWire` / `domainStatus` stores the client status verbatim, and `service/listing.go` `UpdateWithEvent` keeps it. Nothing screens listing content and there is no admin queue (trust-ops findings #1 and #2; backlog Q6 and the listing half of Q23). This slice makes listing status server-owned, adds a write-path auto-screen, and adds the admin moderation RPCs. It also carries the gateway admin-scope routes for the two new RPCs.

initiative: q6-trust-enforcement

## What changes

- **Task 1, quick fix (X3), no new proto needed.** `CreateWithEvent` / `UpdateWithEvent` ignore the client `status` except `DRAFT` and a publish request (`PUBLISHED`); the handler's `domainStatus` maps `UNSPECIFIED` (and every server-only value) to "status omitted" instead of `draft`, so an edit that omits status no longer unpublishes. A seller write to a `REJECTED` listing keeps it `REJECTED` whatever status is sent (sticky). Shipped first and alone; it does not wait for the contract or the screen.
- **State machine owned by the service.** `DRAFT -> (screen) -> PUBLISHED | PENDING_REVIEW`; `PENDING_REVIEW -> PUBLISHED | REJECTED | BANNED` (admin); `PUBLISHED -> REJECTED | BANNED` (admin, for report action); `REJECTED -> PENDING_REVIEW` (seller edit); `BANNED` and `HELD` refuse seller writes and seller deletes with `FAILED_PRECONDITION`; `APPROVE` never reverses `REJECTED` or `BANNED`. An admin's own listing follows the seller path (screen runs) and is still audited; an admin editing another seller's listing keeps its status. `HELD` is entered and left only by the `domain-seller-enforcement-hold` slice; this slice only adds the enum value and refuses seller writes on it.
- **Auto-screen on the write path** (new `internal/screen`): local prohibited-term list first (a minimal seeded list embedded with `go:embed`, overridable by the file `SCREEN_TERMS_FILE`, VI and EN, case- and diacritic-insensitive; a hit gives flag `keyword:<term>` and skips the AI call), then `AIService.ScreenListing` on team-ai through a new `internal/upstream/ai.go` client (service principal `service-team-domain`, scope `ai.classify`, timeout `UPSTREAM_AI_TIMEOUT_SECONDS`, default 2). `REVIEW`, any error, a timeout, or an unset `UPSTREAM_AI_ADDR` gives `PENDING_REVIEW` (fail safe). Flag format `ai:<label>` per returned label. Every seller content edit (title, description, category, images) of a `PUBLISHED` listing re-screens, whatever status the request sends (`PUBLISHED`, omitted or a server-only value), and a flagged edit moves it to `PENDING_REVIEW`; price, stock and variant edits do not; saving a `DRAFT` does not screen.
- **Moderation fields.** New migration adds `moderation_reason_code`, `moderation_note`, `screen_flags` (text array), `moderation_decided_at`, `submitted_at` to `listings`, and a partial index on `(submitted_at, id) WHERE status = 'pending_review'` for the queue. `Listing.moderation` (field 12) is server-set and ignored on writes; `screen_flags` is returned only to admins and service principals; the owner sees `reason_code`, `note` and `decided_at`. Seller writes are conditional on the loaded status and `updated_at` (`FAILED_PRECONDITION` when the row changed since the read).
- **`ModerateListing` and `ListModerationQueue`** on `ListingService` (admin scope only). `ModerateListing`: validate (`INVALID_ARGUMENT`) -> load (`NOT_FOUND`) -> transition check (`FAILED_PRECONDITION`) -> team-audit `listing.moderate` (fail closed, `UNAVAILABLE`) -> status + moderation fields + `ListingChanged(UPDATED)` outbox row in one transaction (`ModerateTx`, conditional on the loaded status and `updated_at`; a concurrent change returns `FAILED_PRECONDITION` and applies nothing). Transitions: `APPROVE` from `PENDING_REVIEW` to `PUBLISHED`; `REJECT` and `BAN` (reason code required) from `PENDING_REVIEW` or `PUBLISHED`; every other source (`DRAFT`, `REJECTED`, `BANNED`, `HELD`) is refused. Audit metadata: `seller_id`, `decision`, `reason_code`, `note`, `from_status`, `to_status`.
- **Admin `UpdateListing` can no longer set status** (Q3 audit behaviour kept: still `listing.admin_update`, `status` metadata now always the stored status). Status moves only through `ModerateListing`. The Q3 e2e scenario that changes status via admin `UpdateListing` is updated by the e2e track.
- **Audit** reuses and extends `internal/upstream/audit.go` `AuditClient` (same service principal and `audit.write` scope, no new client): new method `WriteListingModerate`. The Q3 `AuditWriter` interface gains that method. (The "Q3 SDK helper" named in the brief is this team-domain client; no shared SDK audit helper exists in `platform-core/packages/go-sdk`.)
- **Gateway** (`team-gateway/internal/edge`): `ModerateListing` and `ListModerationQueue` added to `adminProcedures` in `policy.go` (scope `admin`) and forwarded in `listing.go` (`callWrite` / `callRead`); `ScreenListing` stays unrouted and is added to `unrouted_test.go`.
- **Config:** `UPSTREAM_AI_ADDR` (default empty), `UPSTREAM_AI_TIMEOUT_SECONDS` (default 2), `SCREEN_TERMS_FILE` (default empty: the embedded list; a set path that does not exist stops start-up), documented in `.env.example` and README. Vendored protos (listing, ai) are copied after `q6-trust-contract` and regenerated by `make proto`.
- **No new Kafka event.** `ListingChanged(UPDATED)` carries the new status and `moderation.reason_code` / `decided_at`, never the moderation note or the screen flags. team-search needs no change; team-ai indexing only `PUBLISHED` is owned by `ai-listing-screen`.

## Non-functional requirements

- Latency: a content write adds at most `UPSTREAM_AI_TIMEOUT_SECONDS` (2 s) for the screen; keyword check under 5 ms for a 10k-term list; draft saves and non-content edits add no call. `ListModerationQueue` page of 50 within 200 ms p95 at 10k `PENDING_REVIEW` rows (partial keyset index).
- Availability: team-ai down or slow slows publishing (listing goes to `PENDING_REVIEW`), never blocks the write. team-audit down refuses `ModerateListing` (`UNAVAILABLE`); reads, seller writes and queue listing are unaffected.
- Limits: `note` at most 500 characters (counted in runes); one audit event per `ModerateListing` call; `page_size` clamped by the existing `clampPageSize`.
- Visibility: the existing rule (non-`published` hidden from non-owners with `NOT_FOUND`) already covers `PENDING_REVIEW`, `BANNED`, `HELD`.

## Data classification

| field | class | purpose | basis | retention |
|---|---|---|---|---|
| `moderation_reason_code` | non-personal code, tied to a seller's listing | tell the seller why a listing was rejected or banned | platform duty to act against violations (Decree 85/2021) | life of the listing row |
| `moderation_note` (admin free text, 500 chars) | may contain personal data typed by an admin | explain the decision to the seller | same | life of the listing row; audit copy per Q3 policy; never copied into `ListingChanged` events |
| `screen_flags` (`keyword:<term>`, `ai:<label>`) | derived from listing text, not personal | help the admin decide; admin and service principals only (not the owner); never in `ListingChanged` events | same | life of the listing row |
| `moderation_decided_at`, `submitted_at` | non-personal timestamps | queue ordering, decision time | same | life of the listing row |
| `actor_id` (admin) and `seller_id` in the audit event | pseudonymous ids | accountability of the privileged action | legal obligation / legitimate interest (Decree 13/2023 processing records) | team-audit policy, immutable |
| listing title/description sent to team-ai | not personal by design (public product text) | screening | legitimate interest; mock backend sends nothing out of the cluster | not stored by the screen call |

Seller identity is never added to the screen request; only listing id, title, description and category id are sent.

## Threat model

- Assets: marketplace integrity (what is published), the moderation decision record, the audit trail, the `ai.classify` and `audit.write` service principals.
- Abuse cases: (1) a seller publishes or un-rejects by sending `status`, prevented by server-owned status and sticky `REJECTED`; (2) a seller evades the screen by publishing clean text then editing (with status `PUBLISHED`, omitted or server-only), prevented by re-screening every content edit of a `PUBLISHED` listing; (3) a seller bypasses the screen by making team-ai fail, prevented by fail-safe `PENDING_REVIEW`; (4) a seller bypasses the screen through a `price` / `stock` edit that smuggles text, accepted: those fields carry no free text; (5) a non-admin calls `ModerateListing` or reads the queue, prevented by the `admin` scope at the gateway and `RequireScopes("admin")` in team-domain; (6) an admin moderates without a record, prevented by audit-first and fail closed; (7) a caller spoofs the actor, prevented because the actor id is the verified principal id, never a request field; (8) a seller learns which term tripped the screen and rewords around the list, prevented because `screen_flags` are admin-only (stripped for the owner and everyone else); (10) a seller write races a moderation decision and overwrites it, prevented by conditional updates (`FAILED_PRECONDITION`); (11) a seller deletes a banned or held listing to erase the record, prevented by refusing the delete; (9) an admin note leaks personal data to the public, prevented because `moderation` is shown only to the owner, admins and services and the note is never put on the Kafka event.
- Authz rule: `ModerateListing` and `ListModerationQueue` require the `admin` scope (edge 403 for others, 401 anonymous; defence in depth `PERMISSION_DENIED` in team-domain); seller writes keep `listing.write` plus ownership; `ScreenListing` is service-only and not routed.
