## Why

When an admin suspends or bans a seller (identity-user-enforcement), the seller's listings must leave the store and come back when the user is reinstated (initiative story 4). team-identity already emits `UserStatusChanged` on `identity.events`; team-domain owns listing status and has no Kafka consumer yet, so nothing reacts. This slice adds the first team-domain consumer, the `HELD` hold/restore logic and the storage it needs.

initiative: q6-trust-enforcement

## What changes

- New consumer in `team-domain/internal/consumer/` (mirrors `team-search/internal/consumer`: franz-go group consumer, retry with bounded backoff, DLQ on exhaustion) reading `identity.events` with its own consumer group. It decodes `platform.events.v1.EventEnvelope`, handles type `platform.identity.v1.UserStatusChanged` and acknowledges every other type (for example `SessionRevoked`) without action.
- Hold: on `status` SUSPENDED or BANNED, every listing of `user_id` whose stored status is `published` or `pending_review` becomes `held`; its prior status is stored in a new column `listings.held_prior_status`; its moderation reason code becomes `seller_enforcement`; one `ListingChanged(UPDATED)` outbox row per changed listing (status HELD) is written in the same transaction, so team-search and team-ai de-index it through the existing path. Listings in `draft`, `rejected`, `banned` (admin ban) or already `held` are untouched.
- Restore: on `status` ACTIVE or RESTRICTED, every `held` listing of the user returns to `held_prior_status`, the column is cleared, the `seller_enforcement` reason code is cleared, and one `ListingChanged(UPDATED)` row per listing is written. Restore never re-screens or re-queues a listing: a prior `published` listing is re-indexed by that event, and a listing restored to `pending_review` appears in ListModerationQueue again because of its status.
- RESTRICTED from an active user holds nothing. A `SUSPENDED -> BANNED` change keeps the held listings and their original prior status.
- Idempotency: a new table `processed_events(consumer, event_id)` records the envelope event id in the same transaction as the hold/restore; a redelivered event changes nothing.
- Stale-skip: a new table `seller_status_applied(user_id PRIMARY KEY, changed_at)` stores the `changed_at` of the last `UserStatusChanged` applied per user, written in the same transaction. An event whose `changed_at` is not newer than the stored value is skipped (no listing change, event id recorded as processed), the same rule `ai-listing-screen` uses for `ListingChanged`. This keeps a DLQ re-drive or a late older event from re-holding a reinstated seller or restoring a suspended one. A `UserStatusChanged` without `changed_at` is malformed.
- Reservation: `ReserveStock` with a new `reservation_id` on a `held` listing returns `FAILED_PRECONDITION` and leaves stock unchanged (decision M4), so checkout cannot buy from a held seller. A retry with the id of an already active or committed reservation keeps its existing no-op success.
- Delete: owner `DeleteListing` on a `held` listing returns `FAILED_PRECONDITION` (decision A10; the BANNED case belongs to `domain-listing-moderation`).
- Migration `team-domain/migrations/0011_seller_enforcement_hold.{up,down}.sql`: `listings.held_prior_status TEXT NOT NULL DEFAULT ''`, tables `processed_events` and `seller_status_applied`. (Number follows `domain-listing-moderation`'s migration; take the next free number at build time.)
- New config (`internal/config`, `.env.example`, README): `IDENTITY_CONSUMER_ENABLED` (default false), `KAFKA_IDENTITY_TOPIC` (default `identity.events`), `KAFKA_IDENTITY_GROUP` (default `team-domain-seller-hold`), reusing `KAFKA_BROKERS`. Wiring in `cmd/server/main.go` and `internal/bootstrap` as an addon (enable-gated, closed with the lifecycle).
- Vendored proto copy: `team-domain/proto/platform/identity/v1/identity.proto` (from platform-core after `q6-trust-contract`), generated by `make proto`.
- `HELD` is hidden from non-owners exactly like `pending_review` (NotFound on GetListing, absent from public lists); the owner still sees it in ListMyListings with the `HELD` status. Writes by the owner on a `HELD` listing are refused with `FAILED_PRECONDITION` (rule set by `domain-listing-moderation`; this slice only asserts it end to end).
- E2E: platform-e2e feature for suspend -> hidden, reinstate -> back, ban, restricted, plus the seller center view.

No gateway change and no new RPC. No audit event here: the admin action is audited by `SetUserStatus` in team-identity; the hold is its consequence.

## Non-functional requirements

- Latency: listing hold or restore completes within 60 s of the admin action (identity outbox poll + Kafka + consumer), measured from `SetUserStatus` returning to the listing disappearing from search.
- Expired suspension: identity lifts an expired suspension only at the user's next login (decision A15), so a seller who never logs in again stays held. Accepted; a lift sweeper belongs to identity as a follow-up.
- Limits: all listings of a seller are processed in one transaction in batches of 500 rows, with no cap; 5,000 listings is the tested bound, not a limit. One outbox row per changed listing.
- Availability: consumer down only delays the hold; events stay in Kafka and apply on recovery. Handler failure retries with backoff (default 5 attempts) then parks the record on the DLQ topic `identity.events.team-domain.dlq` and moves on; a parked record is a CS alert, not silent.
- Ordering: key is user id, so events of one user are applied in order; the `changed_at` stale-skip covers out-of-order delivery from a DLQ re-drive. Unknown user id (no listings) is a no-op success.
- Unknown status: a `UserStatus` value this consumer does not know (UNSPECIFIED or a future number) is malformed and parked on the DLQ.
- Idempotency: at-least-once delivery, effect once per event id.

## Data classification

| field | class | purpose | basis | retention |
|---|---|---|---|---|
| `user_id` in `UserStatusChanged` / `seller_id` | personal (pseudonymous id) | find the seller's listings | enforcement duty (Decree 85/2021), per the initiative record | consumed, not stored beyond the listing row |
| `held_prior_status` | non-personal | restore the listing | same | until restore; cleared then |
| `reason_code` carried to the listing (`seller_enforcement`) | non-personal fixed code | tell the seller why the listing is held | same | while held |
| `processed_events.event_id` | non-personal | dedupe | operational | purge rows older than 14 days |
| `seller_status_applied.user_id`, `changed_at` | personal (pseudonymous id + time of an enforcement change) | skip stale or re-driven events | same as `user_id` | kept while the account exists; erased with the account |

The admin note and `status_reason` are not read by this consumer and never copied to a listing; the seller sees only the fixed code `seller_enforcement`.

## Threat model

- Assets: seller listings and their visibility; integrity of listing status; the `identity.events` stream.
- Abuse cases: (1) a forged `UserStatusChanged` hides or restores listings, prevented because only team-identity (outbox) produces on `identity.events` and the consumer ignores unknown types; the Kafka ACL on `identity.events` is a deploy item for LOCK.md's human list; (2) a restored listing bypasses moderation, prevented because restore returns only to the stored prior status, an admin-banned or rejected listing is never touched, and a prior `pending_review` returns to the queue; (3) a seller edits a held listing to escape the hold, prevented by `FAILED_PRECONDITION` on seller writes to `HELD`; (4) event replay or reorder (a redelivery, or a DLQ re-drive of an older SUSPENDED after a newer ACTIVE) re-holds or restores the wrong listings, prevented by the event-id dedupe plus the per-user `changed_at` stale-skip; across `SUSPENDED -> BANNED` the prior status is kept because hold only touches `published`/`pending_review` rows; (6) a buyer checks out a held listing, prevented by `FAILED_PRECONDITION` on `ReserveStock`; (5) enforcement note leakage to the seller or listing events, prevented because only the fixed code is propagated.
- Authz rule: the consumer is a system actor, no caller principal; ListingChanged events it emits carry principal `service-team-domain`. Visibility of `HELD` follows the owner-only rule of non-published listings.
