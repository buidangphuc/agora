## Why

team-gateway is the Connect edge of the platform: it verifies RS256 JWTs against team-identity's JWKS, applies the procedure policy tables, forwards every call to 16 upstream gRPC services with a deadline and a read retry, produces browsing beacons to Kafka and consumes session revocations from Kafka. It hand-rolls what the SDK now ships (config loader, logger, tracer and meter, retry, idempotency-key check, Kafka clients, shutdown) and it carries things the user ruled out (`plans/go-sdk-migration/PLAN.md`, decisions of 2026-10-22 and 2026-10-23):

- `KAFKA_ENABLED`: with it false the analytics producer is a `NoopPublisher` and session revocation is silently switched off (revoked tokens stay valid until they expire).
- A private `observability` package (logger, tracer, meter), a reflection-based settings loader and a `SHUTDOWN_GRACE_SECONDS` float, all duplicated by the SDK.
- A hand-written retry loop (`callRead`) and a hand-written Kafka consumer for revocations.
- `EDGE_REFLECTION_ENABLED`, a gateway-only name for the flag the SDK names `GRPC_REFLECTION_ENABLED`.

The gateway moves onto go-sdk `v1.0.2` where the SDK covers the job, and stays hand-written where it does not (the Connect handler chain, the JWT verifier, the policy tables, the principal forwarding). Importing Kafka means using it: after this change the gateway cannot start without a Kafka client configuration and no no-op or in-memory path ships in the binary.

initiative: go-sdk-migration

## What Changes

- Require go-sdk `v1.0.2` in `team-gateway/go.mod`: no `replace`, no `third_party`. The Makefile sets `SERVICE`, `GRPC_PORT`, `BINARIES := gateway` and includes `../platform-core/make/go-service.mk` with `LINT_CONFIG := ../platform-core/packages/go-sdk/.golangci.yml`; `golangci-lint` is pinned as a `tool` line like the SDK `go.mod`. No new doc comments are written (the shared revive rules are off).
- ADR-0016 layout: `cmd/gateway/main.go` calls `internal/app.Run(ctx, settings)`; `internal/config` (SDK `config.Load`), the unchanged domain packages `internal/edge` (the Connect handler layer, which takes the place of `internal/rpc`), `internal/token`, `internal/revocation`, `internal/events`, `internal/upstream`. `internal/observability` and `internal/config/envcheck.go` are deleted.
- **REMOVED (behaviour)** `KAFKA_ENABLED`, `events.NoopPublisher`, the "revocation disabled" boot path, the hand-rolled settings loader, `observability.*`. **BREAKING** for any deployment that sets them: `KAFKA_ENABLED` is simply no longer read (compose and gitops lines are removed by `deploy-go-sdk-v1`).
- **CHANGED (renamed keys)** `HTTP_HOST` to `GRPC_HOST`, `HTTP_PORT` to `GRPC_PORT` (required), `SHUTDOWN_GRACE_SECONDS` to `SHUTDOWN_GRACE` (Go duration, default `10s`), `EDGE_REFLECTION_ENABLED` to `GRPC_REFLECTION_ENABLED` (off by default, accepted only when `ENV` is `local` or `test`), new `SHUTDOWN_DRAIN_DELAY`. `ENV` is required (no `local` default). `KAFKA_BROKERS` is required in a strict ENV.
- **KEPT** every edge key that is not an SDK group key (`RATE_LIMIT_*`, `TRACK_RATE_LIMIT_*`, `CALL_TIMEOUT_SECONDS`, `AI_CALL_TIMEOUT_SECONDS`, `RETRY_MAX`, `STREAM_*`, `DIAL_TIMEOUT_SECONDS`, `JWKS_CACHE_TTL`, `PUBLIC_SCOPES`, `CORS_ORIGINS`, `TRUSTED_PROXIES`, `PROMETHEUS_URL`, `JAEGER_*`, `UPSTREAM_*_ADDR`, `KAFKA_ANALYTICS_TOPIC`, `IDENTITY_EVENTS_TOPIC`), so the e2e private-gateway steps and the compose environment keep working.
- **CHANGED** health: the gateway serves the standard `grpc.health.v1.Health/Check` through its Connect mux, backed by `healthx`: service `""` (readiness) is SERVING only once the JWKS has been fetched at least once and the revocation consumer has read up to the end offset of every partition captured when it started; Kafka itself is not a readiness check (no producer ping check; the consumer state is reported through `gateway_revocation_consumer_up`); service `liveness` is SERVING from start and independent of every dependency; both turn NOT_SERVING on shutdown drain. `GET /healthz` is unchanged (200 `ok`, process only). The gateway holds no database, so it has no Postgres check and no `migrate up` subcommand.
- **CHANGED** Kafka: the analytics producer is `kafkax.Producer` (trace and request-id headers on every record), the revocation consumer is a `kafkax.NewConsumerClient` with an empty group (every replica reads every partition from the earliest offset, no consumer group is created). Both always run. A produce failure is still logged and the beacon is still accepted; the publish is now bounded by `TRACK_PUBLISH_TIMEOUT` (default `2s`).
- **CHANGED** upstream reads: `callRead` runs under `resilience.Retry` only (only `Unavailable` is retried, `RETRY_MAX` retries, 50 ms to 200 ms jittered backoff). There is NO circuit breaker (human decision 2026-10-23): no `UPSTREAM_BREAKER_*` key and no per-service breaker. Writes and AI generation calls stay single attempt.
- **CHANGED** telemetry and logs: `logx` and `otelx` replace `observability`; the `edge.request` line keeps its fields and gains `principal_id` and `trace_id` from the SDK handler. The SDK validators replace the local Idempotency-Key check; `jwtx` supplies the JWKS and claims wire types.
- **BREAKING (defaults)** the previous default was `KAFKA_ENABLED=false`: a gateway started with only the defaults ran a no-op producer and accepted beacons without a broker. It now reports readiness NOT_SERVING until the revocation consumer has caught up, which needs a reachable broker with the `identity.events` topic, so e2e helpers and local runs that relied on the old default must be reviewed (the e2e track lists them). After catch-up a broker outage no longer changes readiness.
- **BREAKING (strict ENV)** two sets now exist on purpose: reflection is refused for every `ENV` other than `local` and `test`, whereas `KAFKA_BROKERS` and `MOCK_DATA` are refused only for staging, stage, prod and production. An `ENV` such as `dev` or `development` used to refuse nothing; it now refuses reflection (deliberate tightening of today's staging-and-production-only rule).
- **CHANGED** JWKS boot: `Verifier.Prime` still runs at boot (5 s bound, warn, boot continues) and is now retried every 5 s in the background until the first success, so readiness cannot deadlock on a pod that starts before identity.
- **CHANGED** read failures: an error caused by the caller's context (cancel, or a deadline shorter than `CALL_TIMEOUT_SECONDS`) is not retried.
- **CHANGED** idempotency key: the check spec is now explicit (repeated header refused, whitespace trimmed first, applies to `CreateOrder`); behaviour is unchanged.
- **ADDED** capability `gateway-service-runtime`. **MODIFIED** `edge-stream-and-http-policy` "Edge reflection is off unless enabled, and never in staging or production" and `tracking` "Telemetry emission is best-effort and does not block browsing" (the no-op on `KAFKA_ENABLED=false`). The shared `deploy-runtime` requirement "Services refuse unsafe configuration in staging and production" is NOT modified here: only change `deploy-go-sdk-v1` modifies shared deploy-runtime requirements, and the needed team-gateway bullet is listed under the Deploy track in `tasks.md`.
- Deploy work (compose block, gitops baseline, argocd inline values, staging and prod overlays) is listed in `tasks.md` under "Deploy track" and done by change `deploy-go-sdk-v1`, not here.

Not adopted, with the reason (see design): `upstream.NewClient` (it deletes the anonymous principal metadata, adds a 2 s default bound and a 500 ms deadline margin, so it would change what the 16 services receive), `grpcx.NewServer` and `grpcx.Status` (the gateway serves Connect, not a gRPC server; its error mapping is Connect-to-Connect), `auditx` (the gateway writes no audit event), `outbox`, `postgres`, `migrate`, `idempotency` dedupe (the gateway holds no database), `flags` (no flag evaluation at the edge today), `pagination` (list RPCs are forwarded, not paged here), `consume` (the revocation consumer has no group, no commit and no DLQ).

## Impact

Code: everything under `team-gateway/` except `proto/`. Specs: `gateway-service-runtime` (new), `edge-stream-and-http-policy`, `tracking`. No proto change, no new RPC, no new event. E2E: `team-gateway/FEATURES.yaml` entries; the e2e files that name retired keys (listed in tasks 2.2) change in the e2e track. Every `UPSTREAM_*_ADDR` is required in every `ENV` and no dependency has a fallback mode (unchanged for the gateway).

Merge ordering: this change alone leaves `docker-compose.services.yaml` (`HTTP_PORT`, no `ENV`) unbootable and any consumer of the gitops baseline that lacks an overlay setting `ENV` (for example the local ApplicationSet values) crash-looping, because `ENV` and `GRPC_PORT` are now required. It SHALL land in the same merge as `deploy-go-sdk-v1`; the baseline `platform-gitops/envs/services/team-gateway.yaml` is deliberately left without `ENV`, so every overlay and the argocd inline values must set it.

## NFR

- Boot: `Run` returns an error in under 2 s for an invalid configuration (refusals happen in `config.Load`, before any dial); an unreachable Kafka or identity does not fail boot, it keeps readiness NOT_SERVING (until the denylist has caught up and the JWKS was fetched).
- Health: readiness becomes SERVING within one `healthx.DefaultInterval` (5 s) plus the catch-up time of the denylist after the broker answers; after that a Kafka outage does not flip it. The `liveness` service answers from memory (p99 under 5 ms) and stays SERVING while Kafka or identity is down, so a dependency outage never restarts a pod. Once the JWKS was fetched, an identity outage does not flip readiness (cached keys keep verifying until a key rotation needs a fetch).
- Request path: the added work per call is one in-process check (SDK validators); no new network hop; `/api/track` publish waits at most `TRACK_PUBLISH_TIMEOUT` (2 s) for the broker, so a broker outage cannot hold a browser request longer than that.
- Read retry: at most `RETRY_MAX + 1` attempts (default 3), backoff 50 ms doubling to 200 ms with 25 % jitter (about 0.05 s then 0.1 s, at most 0.19 s in total with jitter), each attempt bounded by `CALL_TIMEOUT_SECONDS` (5 s). Worst-case total latency of one read with the defaults is 3 x 5 s + 0.19 s = about 15.2 s, reached only when every attempt fails `Unavailable` just before its timeout (a timed-out attempt is `DeadlineExceeded` and is not retried, so a timeout-only read ends after 5 s). The retry loop stops as soon as the caller's context is done (cancel or `Connect-Timeout-Ms`). With no breaker, a recreated upstream is reachable on the next read.
- Revocation: a revoked session is rejected within 5 s of the event (unchanged); a replica reports ready only after the denylist has been replayed to the end offset captured at start (so it never serves tokens revoked before it started); on restart the denylist is rebuilt from the earliest offset (unchanged; topic retention must be at least the token TTL).
- Shutdown: SIGTERM turns health NOT_SERVING, waits `SHUTDOWN_DRAIN_DELAY` (default 0), then stops the HTTP server within `SHUTDOWN_GRACE` (default 10 s), of which a fifth (at most 2 s) is kept for closing the producer, the upstream connections and telemetry.
- Limits unchanged: rate limits (default 20 rps, burst 40; track 5 rps, burst 20), `STREAM_MAX_REQUEST_BYTES` 16384, request id of 1 to 64 characters, Idempotency-Key of 1 to 255 printable ASCII characters.
- Availability: stateless; N replicas; the in-memory denylist and rate-limit buckets stay per replica (unchanged).

## Data classification

| Field | Where | Purpose | Consent basis | Retention |
|---|---|---|---|---|
| principal id (`sub`) | request logs (`principal`, `principal_id`), traces, forwarded as `x-principal-id`, `EventEnvelope.principal` | authorization, abuse tracing, attribution of telemetry | legitimate interest (operating the platform) | platform log retention; the gateway stores nothing else |
| session id (`sid`) | in-memory denylist only | reject revoked sessions | legitimate interest (security) | until the revoked token's expiry (entry pruned), never logged |
| client IP, user agent | forwarded as `x-client-ip`, `x-client-user-agent` | audit fields in services | legitimate interest (security audit) | not stored by the gateway; request logs carry neither |
| beacon fields (session id, anonymous id, listing id, event properties) | `analytics.events` records | behavioural analytics | analytics consent cookie, enforced by the collector (`tracking-consent`, unchanged) | topic retention (unchanged); Kafka record key is the session id (unchanged) |
| bearer token | request header only | authentication | contract | never stored or logged |

The gateway logs no Kafka record key (the revocation consumer logs partition and offset only), so `LOG_KEY_FP_SECRET` is not a gateway setting. Request bodies and query text are never logged. DPO sign-off is not required (user rule 2026-10-23): basis legitimate interest, platform log retention.

## Threat model

- Assets: the principal headers the gateway mints for 16 services, the JWKS trust anchor (`JWKS_URL`), the in-memory revocation denylist, the analytics topic, the rate-limit buckets, the `TRUSTED_PROXIES` list.
- Abuse 1, principal spoofing: a client sends `x-principal-*`, `x-client-*` or `x-request-id` headers. Control (unchanged): the gateway builds every forwarded value fresh from the verified token and edge-observed values; the SDK constants replace the string literals only.
- Abuse 2, token downgrade: a present but invalid bearer is answered `unauthenticated`, never downgraded to anonymous (unchanged). A JWKS that was never fetched makes readiness NOT_SERVING, so no pod serves traffic without the ability to verify tokens.
- Abuse 3, silent loss of revocation: with `KAFKA_ENABLED=false` revoked tokens stayed valid. Control: no flag; the consumer always runs; readiness stays NOT_SERVING until the consumer has read up to the end offset captured at start, so a fresh replica never serves while its denylist is behind; `gateway_revocation_consumer_up` is 0 while the consumer cannot read (broker unreachable, topic missing, ACL denied). Residual risk: after catch-up a broker outage leaves the replica serving with a denylist that stops growing until the consumer recovers (the gauge shows it); accepted by the rule that Kafka is not a readiness check.
- Abuse 4, reflection or mock data left on in production. Control: `GRPC_REFLECTION_ENABLED` and `MOCK_DATA` are refused by `config.Load` unless `ENV` is `local` or `test` (reflection) or not strict (mock data), before validation; the gateway declares no `MOCK_DATA` adapter.
- Abuse 5, retry storm against a failing upstream. Control: bounded retries (`RETRY_MAX`) with jitter, Unavailable only; writes never retried. There is no breaker (human decision).
- Abuse 8, probe path abuse: an unauthenticated caller hits the health handler. Control: it returns only SERVING or NOT_SERVING, bypasses auth and the rate limit by design, and is mounted before the policy tables.
- Abuse 6, beacon flood or a stuck broker holding browser requests. Control: separate per-visitor track bucket (unchanged) and the `TRACK_PUBLISH_TIMEOUT` bound.
- Abuse 7, X-Forwarded-For spoofing. Control (unchanged): honoured only from a peer in `TRUSTED_PROXIES`.
- Authz rule (unchanged): the edge resolves the principal from the bearer token; the procedure policy tables (`requireProcedureScope`, `adminProcedures`) gate each procedure before forwarding; anonymous callers get `PUBLIC_SCOPES`; the health service, `/healthz` and reflection (when enabled) carry no data and need no principal.
