## 3. Rollout order (run by a human, per environment)

1. Merge the service changes, this change and the image bump together. The new images refuse to boot without `ENV`, `DATABASE_URL` (and `GRPC_PORT` from the image), and a pod whose liveness probe names `liveness` needs the new image; so the manifests and images ship in one sync.
2. Provision Vault (section 4) before the sync.
3. First rollout of an outbox service (chat, payment, engagement, domain, order, identity): scale the old Deployment to 0 and wait until no pod runs; disable auto-sync and `selfHeal` for the Application first, then sync once with the overlay line `strategy: {type: Recreate}` committed with the image bump (removed in the follow-up commit, auto-sync re-enabled); the PreSync Job `migrate up` runs first (requeues parked rows; engagement `0014` copies legacy rows; order `0011` to `0022`; identity `0019`; domain `0016`); then the new pods start. Never two relayers. If the Job fails the service is down: follow the failure section of `outbox-first-rollout.md` (restore within 30 minutes). Promotion: no scale-down needed (new table).
4. Services without outbox (verification, search, audit, notification, gateway, analytics): normal rolling sync; the PreSync Job (database services) runs before the pods change.
5. Rollback: revert the image tag only for services without an outbox migration; for outbox services drain the new outbox table first (see each service's design).
6. Later rollouts use the default strategy.
