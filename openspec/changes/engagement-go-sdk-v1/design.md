### D2 No enable flags, no runtime fallbacks

Deleted: `DATABASE_ENABLED`, `KAFKA_ENABLED`, the "KAFKA off, facts stay in the outbox" branch, `UPSTREAM_ORDER_ADDR` or `UPSTREAM_AUDIT_ADDR` empty disabling a feature (nil `OrderClient`, nil audit client), `handler.Option` nil checks that answer `Unimplemented` ("reviews service unavailable" and the like), `WithAudit` optional wiring, `bootstrap.OpenResources` refusing `DATABASE_ENABLED=false`, `UPSTREAM_CALL_TIMEOUT_SECONDS`. Kept: `OTEL_ENABLED`, `GRPC_REFLECTION_ENABLED`; the SDK refuses reflection whenever `ENV` is not `local` or `test` (so `ENV=dev` is refused for reflection yet is not strict for brokers and secret, which only staging, stage, prod and production are). There is no `SEED_ADMIN_ENABLED` here. Existing mock switches: none in this service, so nothing moves onto `pkg/mockdata`; `MOCK_DATA` is not declared (a service declares the group only when it has an adapter to mock).

Every upstream the service calls has a required address in every `ENV` (Round 2, item 6): `UPSTREAM_ORDER_ADDR` has no SDK group, so this service validates it; `UPSTREAM_AUDIT_ADDR` is optional in the SDK `config.Audit` outside strict `ENV`, so the service adds a check after the SDK groups that refuses an empty value in every `ENV`. The composition root therefore always builds the order client and the audit connection (`auditx.Dial` never returns nil), the gate always has a writer, and the typed-nil hazard does not arise. A review or dispute without team-order, or an admin action without team-audit, could only ever answer `Unavailable`, so a deployment without either is a misconfiguration, not a mode. The existing e2e compose block already sets both addresses, so no extra deploy edit is needed.

### D3 Readiness covers Postgres only

Human decision, Round 2 item 2: Kafka is not a readiness check in any service; readiness is Postgres plus required upstream health checks, and engagement has no upstream health check (team-order and team-audit are called per request).

`healthx.New(healthx.DefaultInterval, logger)`, `Register("postgres", postgres.Checker(pool))`. Kafka is not a readiness check: writes go to the outbox in Postgres and wait there while Kafka is down (the `engagement-facts` scenario "A fact written while Kafka is down is published later"), and the feed consumer retries. Marking every pod NOT_SERVING during a broker outage would take reviews, favourites and disputes down for nothing. Chart: `probes.livenessService: liveness`.

### D4 Outbox on `outbox.Store`

Table `engagement_outbox_events` is `outbox.SchemaSQL("engagement_outbox_events")`, shipped as migration `0014` (migrations `0001` to `0013` exist). The SDK publishes `Row.Payload` verbatim, so `events.FactRow` builds the whole `platform.events.v1.EventEnvelope` at write time (fresh `uuid` event id, payload full proto name as `type`, caller principal from `sdk/auth`, request id from `reqctx`, `occurred_at` now) and the row carries `AggregateType` (`Listing`, `Seller`, `Dispute`) and `AggregateID` (the old key). Relay is per aggregate in `seq` order, so ordering is per record key; the old relayer ordered globally with an advisory lock. Consumers (analytics, order) dedupe on event id and key, not on a global order. `outbox.Relayer` retries transient errors forever with capped backoff and parks only `outbox.Permanent` errors, so a Kafka outage never parks a fact. Retention: `lifecycle.Every(time.Hour, func(ctx) { store.Purge(ctx, 7*24*time.Hour) }, RunAtStart)` in the service replaces the in-relayer trim; the SDK `Store.Purge` deletes only published rows older than 7 days (Round 2, item 4).

Migration `0014` creates the table and copies every unpublished row of the old `outbox` table (event id kept, `created_at = occurred_at`, payload becomes the marshalled envelope, `available_at` strictly increasing in old `seq` order so the relayer claims them in the old order). Reference implementation: `git show origin/feat/go-sdk-v1-e2e:team-engagement/migrations/0011_engagement_outbox_events.up.sql` (builds the protobuf bytes in SQL, byte-equal to the Go marshaller). Rerun is a no-op (`ON CONFLICT DO NOTHING`). After the copy the migration requeues every row of the new table parked as `failed` (the SDK's `RequeueParked` statement: `status = 'pending'`, attempts 0, lease and error cleared), so no parked row can block its aggregate under the SDK relayer (Round 2, item 4). The legacy table has no parked state (the old relayer retried forever), so on the table `0014` creates the requeue touches nothing; it matters only when the table already exists with parked rows, which the migration test covers (`TestMigration0014RequeuesParkedRows`).

Rollback rule: roll forward only. After `0014` the new pod writes facts only to `engagement_outbox_events`, which the previous image never relays, and the down migration drops that table, so reverting the image strands or deletes those facts. To roll back anyway, first let the new relayer drain the table (no row with `published_at` NULL), then stop the new pod, then revert the image; the down migration is for an empty table only. The old table is neither written nor dropped (down migration drops only the new table); dropping it is a later cleanup change.

First rollout (Round 2, item 4): never two relayers, and no fact written to the legacy table after the copy. The old pods are scaled to 0 and gone before the migrate job copies the legacy rows and before any new pod starts (one Recreate, not a rolling update); then `migrate up` (PreSync job in gitops, `team-engagement-migrate` in compose) applies `0014`, then the new pod starts with its relayer. A fact the old pod committed and had not yet relayed is copied by `0014`; one it had relayed just before stopping may be copied too and is duplicated once, which downstream event-id dedupe absorbs. Later rollouts use the normal strategy (one image, one relayer set; `outbox.Relayer` claims with `SKIP LOCKED`, so overlapping pods also publish each row once).

`DisputeResolved` keeps its atomic compare-and-set: `store.ResolveWithEvent(ctx, d, prev, fact)` updates the dispute and calls `factWriter.enqueue` in one `postgres.WithTx`; a loser of the race writes no fact.

### D5 Audit-first on `auditx`

`upstream.AuditWriter` implements `auditx.Writer` (`WriteAuditEvent(ctx, auditx.Event)` calls `team-audit WriteAuditEvent` with actor, action, target type, target id and metadata exactly as today: `review.hide`, `dispute.resolve`, `report.resolve` with the same metadata keys). The connection comes from `auditx.Dial(settings.Audit, "service-team-engagement", "audit.write")`; the SDK sends the id verbatim, and `service-team-engagement` is the value the unmodified specs `review-moderation`, `dispute-audit` and `report-resolution` require, so the id does not change. The order client uses the same id with scope `order.read` (`upstream.AsService("service-team-engagement", "order.read")`, default 2 s call bound) for `GetOrder` and `GetReturn`. Services call `gate.Do(ctx, ev, action)`: validation, load and transition checks stay before the gate, the state change is the action. The action's error is returned unchanged, so "Update failure after audit is Internal and retryable" (two audit events after a retry) holds. The gate's write timeout is fixed at 2 s and is the only bound on the write (no `UPSTREAM_CALL_TIMEOUT_SECONDS`, no `upstream.Bounded` in the writer). The client-visible text becomes `audit trail unavailable` (code `Unavailable` unchanged).

### D6 Errors on one `grpcx.ErrorTable`

`internal/rpc/errors.go` builds the table once at `Register` with `grpcx.Rule{Target, Code, Message}` for every domain error, each with today's code and today's client-visible message (the complete list is the table of the requirement "gRPC errors go through one error table"; the `Message` is set on every rule whose handler text differs from the sentinel's, for example `ErrOrderNotEligible` sentinel text `order not eligible for review` versus the client text `order is not eligible for review`). Rules come before the SDK's 23505 default, so `ErrDuplicateReview` and `ErrOpenDisputeExists`, which wrap a 23505, keep `review already exists for this order and listing` and `an open dispute already exists for this return` instead of the SDK's `already exists`. `ErrAuditUnavailable` is deleted with the nil audit client; the gate's `Unavailable` is a status error that `grpcx.Status` passes through, so it has no rule. `upstream.ErrOrderNotFound` and `upstream.ErrReturnNotFound` have rules because the dispute and return-linked paths return them. The `CreateDispute` outcomes that are decided by the handler from a team-order answer (order not owned by the caller, defendant mismatch, return of another order, `can_escalate` false, a failing lookup) stay explicit `status.Error` with today's code and text; they are not sentinel errors. Request validation that names a field stays explicit. Every other return goes through `grpcx.Status(ctx, logger, err, table)`; `status.Errorf(codes.Internal, "list reviews: %v", err)` style leaks of wrapped text disappear. The party checks stay explicit too, with today's code and text: `CreateDispute` by a stranger `NotFound` `order not found` (no dispute row), `GetDispute` by a stranger `NotFound` `dispute not found` (identical to a missing id, so ids cannot be probed), `ListOrderDisputes` by a non-party or for an unknown order `PermissionDenied` `not a party to this order`, and its failing lookup `Unavailable` `order verification unavailable`. The shop-reply rule is a downgrade, not a denial: `AnswerQuestion` with `is_shop_reply` by a non-owner returns OK and stores an ordinary answer. The error table lists every sentinel by name (the request-validation ones too); Cursor errors keep today's behaviour per RPC and are stated exactly in the spec: only `ListFollowedListings` maps `ErrInvalidCursor` (`InvalidArgument` `invalid cursor`, a table row); `ListReports` answers `invalid cursor` and `ListReviews` `invalid page cursor` from explicit handler checks of an integer offset; `ListDisputes` with a bad cursor answers `Internal` `internal error` today and keeps doing so (the other lists use an id keyset that is never validated); `upstream.ErrOrderIDRequired` has no rule because the review service rejects an empty order id before the verifier. `ErrDisputeNotInState` (lost compare-and-set race) answers `FailedPrecondition`, as the C4 scenario "Concurrent resolutions apply once" requires; today's handler would have returned `Internal` for it, which is a fix.

### D7 Auth

The hand-written metadata parser, `RequireScopes` and `PrincipalFromContext` are replaced by `sdk/auth` (`auth.UnaryInterceptor` is part of `grpcx.NewServer`; helpers `RequirePrincipal`, `RequireScopes`, `RequireUser`, `RequireService`). The ownership checks (order parties, listing owner) stay in `engagement`/`rpc`. Gates stay exactly as they are today, 36 RPCs: 5 admin (`HideReview`, `ResolveDispute`, `ListDisputes`, `ListReports`, `ResolveReport`: authenticated plus `admin` scope), 14 `engagement:write`, 10 `engagement:read` and 7 public with no check (`RecordView`, `GetRecentlyViewed`, `GetListingStats`, `ListReviews`, `GetListingRatingSummary`, `GetShopRatingSummary`, `ListQuestionsByListing`); the per-RPC table is in the spec and `TestEveryRpcHasItsGate` walks the generated service descriptor so a new RPC cannot ship unclassified. No gate is added or removed here (adding a scope to the public reads would break anonymous browsing, and is a separate decision). The envelope principal is built from `auth.Principal` (`events.principalFrom`).

### D8 Consumer

`kafkax.NewConsumerClient(settings.Kafka, group, []string{topic}, kgo.ConsumeResetOffset(kgo.NewOffset().AtStart()))` keeps the "fresh group backfills the feed from the start" behaviour; `consume.NewConsumer(client, handler, producer, consume.Options{DLQTopic: topic + ".dlq", KeyFP: fp, Logger: logger})` with `fp := kafkax.NewFingerprinter(settings.LogKeyFP.Secret)`. Defaults 5 attempts, 100 ms to 30 s backoff, one commit per fetch. The handler (`ListingEventHandler`) is kept as is apart from its signature `func(ctx, consume.Record) error`; a malformed record returns `consume.Permanent(err)` so it goes straight to the DLQ instead of burning five attempts (observable difference: 1 attempt, not 5, for undecodable bytes). A fatal consumer error ends `lifecycle.Run` and the process exits non-zero. One `kafkax.Producer` serves the relayer and the DLQ.

### D9 Pagination

`pagination.Clamp` replaces the three `clamp*` helpers (feed and favourites 50/100, disputes `defaultDisputePageSize`/`maxDisputePageSize`, reports 100) and the ad hoc rule in `ListQuestionsByListing` (default 20, maximum 100; Round 2, item 13: today a size above 100 falls back to 20, afterwards it is capped at 100). Cursor encodings are kept byte-for-byte: feed cursor `feedCursor`, dispute cursor `base64url("<unix-micro>|<id>")`, report cursor, review offset cursor. A cursor minted before the migration must decode after it.

### D10 Report retention sweep

`bootstrap.RunReportSweepLoop` becomes `lifecycle.Every(settings.Reports.SweepInterval, sweep, RunAtStart, WithLogger)`; `engagement.SweepReports` (batches of 500, resume after a failed batch) is unchanged. It is a worker stopped after the gRPC server.

### D11 Shutdown order

`lifecycle.Run` with `OnShutdown: health.Drain`, `DrainDelay`, then `lifecycle.StopAfter(grpcx.Serve(srv, settings.GRPC), relayer, retention, sweep, listingConsumer)`, then closers (producer, consumer client, upstream connections, pool) in reverse.

### D12 Tooling, port and migrations

`go.mod` requires the tag; `golangci-lint` is pinned as a Go tool (`tool github.com/golangci/golangci-lint/v2/cmd/golangci-lint`, same version as the SDK go.mod). `Dockerfile` keeps `ENV GRPC_PORT=50054` because the SDK declares `GRPC_PORT` as required with no default and the gitops baseline does not set it; `.env.example` lists `GRPC_PORT=50054` and the compose block keeps it. `Makefile` sets `SERVICE`, `GRPC_PORT := 50054`, `LINT_CONFIG := ../platform-core/packages/go-sdk/.golangci.yml` and `include ../platform-core/make/go-service.mk`; no per-service lint config and no copy of the make file. No doc comments are added (revive doc rules are off).

Migrations (Round 2, item 1): the binary implements `migrate up` (`main` dispatches `os.Args[1:] == ["migrate", "up"]` to `app.Migrate`, which loads only the `Runtime` and `Postgres` groups and calls the SDK `migrate.Up(ctx, url, fs.Sub(migrations.FS, "."))` on the embedded files); the service never migrates at boot. The shared `make migrate` (`go run ./cmd/server migrate up`) now works as is, so the service Makefile no longer overrides it. The image is the migrate image: compose keeps a `team-engagement-migrate` service that runs the service image with `migrate up` and that `team-engagement` waits for, and gitops runs an Argo PreSync migrate Job per service (both in change deploy-go-sdk-v1, Deploy track below). The service role `engagement_svc` runs both, as in compose today.

## Risks and trade-offs

- Ordering per key instead of global: accepted by the user for all SDK adopters; no engagement consumer relies on cross-key order (analytics and order handle one record at a time and dedupe on event id).
- Facts of the old table copied at cut-over can duplicate one that the old relayer published just before stopping; downstream dedupe covers it. The first rollout needs a Recreate (scale to 0) rather than a rolling update; later rollouts do not.
- `OUTBOX_POLL_INTERVAL` default is 1 s (was 500 ms); compose keeps 500 ms through the env var (deploy track).
- Accepted: a deployment that set `UPSTREAM_CALL_TIMEOUT_SECONDS` above 2 s now gets 2 s; `ListQuestionsByListing` with a page size above 100 now returns 100 items instead of 20; a deployment without `UPSTREAM_AUDIT_ADDR` no longer starts (it only ever answered `Unavailable` to admin actions).
- Immediate DLQ for undecodable bytes changes the retry count for poison records only.
- This change builds on code of `engagement-dispute-escalation` and `engagement-listing-reports` that are merged on the branch but not archived; the new requirements do not MODIFY their unarchived requirements, they restate the runtime facts (`DisputeResolved` row, audit gate) in terms of SDK parts.
