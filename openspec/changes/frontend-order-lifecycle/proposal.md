## Why

After checkout the buyer UI stops short of the new backend lifecycle (initiative q10-order-lifecycle). An online order that is not paid is cancelled by the system after 24 hours, but no screen shows the deadline, the pay page 404s when no transaction exists, and its text claims a failed payment cancels the order (it does not: a FAILED payment leaves the order PENDING). A shipped order can now be confirmed by the buyer ("Đã nhận được hàng") or completed by the system after 7 days, but there is no button and no hint. The detail page offers cancel on SHIPPED orders (the backend refuses it) and offers returns only on COMPLETED orders (the backend now accepts them on SHIPPED orders and for 15 days after completion). The cancel dialog sends only a free-text label. The seller dashboard counts unpaid online orders as work and shows no ship-by deadline (backlog Q10, Q20, Q9 and the cancel-UX part of Q12; `buyer-journey.md` #4, #6, #9, `seller-success.md` #4).

initiative: q10-order-lifecycle

depends_on: payment-unpaid-cancel (a cancelled unpaid order has a CANCELLED transaction that `ProcessMockPayment` refuses), order-receipt-completion (`OrderService.ConfirmReceipt`, `Order.payment_due_at/ship_by/shipped_at/completed_at/return_window_ends_at/cancel_reason/auto_complete_at`, return acceptance on SHIPPED and inside the window, and the team-gateway `ConfirmReceipt` forwarder, which that slice owns), notification-order-work (the notifications whose links this UI must resolve), and transitively q10-order-lifecycle-contract (`CancelOrderRequest.reason_code`, `CancelReason`, the Order fields). No proto is edited here; `team-frontend/proto` and `src/generated` are refreshed from the contract slice (task 0).

## What Changes

Gateway route check (every RPC this UI calls, against `team-gateway/internal/edge`): `CreateOrder`, `GetOrder`, `ListBuyerOrders`, `ListSellerOrders`, `UpdateOrderStatus`, `CancelOrder`, `CreateReturnRequest`, `ListOrderReturns`, `UpdateReturnStatus`, `GetShipmentTracking`, `GetSagaState`, `CreatePayment`, `GetPayment`, `ProcessMockPayment` and `NotificationService.ListNotifications` already have forwarders. `OrderService.ConfirmReceipt` has none today (the generic handler would answer 501 Unimplemented, the Q5 `CalculateShippingFee` failure); it is added by order-receipt-completion (its repos touched include team-gateway), so this slice adds no gateway code, but its e2e track proves the route end to end through the UI (scenario "Order lifecycle: the buyer confirms receipt and the review prompt opens"). No other route is new.

- **Gateway wrappers** (`src/lib/gateway/orders.ts`, `payment.ts`): `ViewOrder` gains `paymentDueAt`, `shipBy`, `shippedAt`, `completedAt`, `returnWindowEndsAt`, `autoCompleteAt` (ISO-8601 strings, `""` when unset, so a server component can compare them with `Date.now()`; display text comes from a formatter) and `cancelReason` (`CancelReason`). New `confirmReceipt(id)`. `cancelOrder(id, reason, reasonCode)` sends `reasonCode`. `getPaymentStatusText` names `PAYMENT_STATUS_CANCELLED` ("Đã hủy").
- **Lifecycle rules in one module** (`src/features/order/lifecycle.ts`, pure, takes `now`): `isOnline(order)` (payment method not COD and not UNSPECIFIED), `paymentExpired(order, now)` (`payment_due_at` set and `now >= payment_due_at`), `canPayAgain(order, now)` (PENDING, online, not expired), `canCancel(status)` (PENDING or PAID only), `canConfirmReceipt(status)` (SHIPPED), `canReturn(order, now)` (SHIPPED; or COMPLETED with `now < return_window_ends_at`; a COMPLETED order with no `return_window_ends_at` is offered the action and the server decides). `OrderDetailView.canCancelFromDetail` / `canReturnOrder` and `OrderList.canCancelFromList` delegate to it. Server components compute the booleans and pass them down so a client island never reads the clock.
- **Cancel UX** (`OrderActions.tsx`, new `src/features/order/cancelReasons.ts`): the reason list moves to a shared module with `{ value, label, code }` (`changed_mind` -> `CANCEL_REASON_CHANGED_MIND`, `wrong_item` -> `WRONG_ITEM`, `damaged` -> `DAMAGED`, `delivery_delay` -> `DELIVERY_DELAY`). `cancelOrderAction(orderId, reasonValue)` looks the value up server side and calls `cancelOrder(id, label, code)`; an unknown value is refused with "Lý do hủy không hợp lệ." and no call. The client can never send `PAYMENT_EXPIRED` or `ADMIN_FORCE_FAIL` because only the table's four codes are reachable (and the backend answers `PERMISSION_DENIED` to a buyer sending a system-only reason, B9). The detail offers cancel for PENDING and PAID only; a SHIPPED order offers "Yêu cầu trả hàng" and "Đã nhận được hàng". The list keeps cancel for PENDING only (a subset of what the backend allows).
- **Payment deadline and retry**: order list rows and the detail header show "Hạn thanh toán: <date time>" for an online PENDING order with a deadline, and a "Thanh toán lại" link to `/checkout/pay/{id}` (replacing "Thanh toán ngay") while `canPayAgain`. At or after the deadline the link is replaced by the text "Đã hết hạn thanh toán" (the sweep cancels the order up to one sweep interval later). A COD order shows neither. The detail of an order cancelled with `cancel_reason = PAYMENT_EXPIRED` shows "Đơn hàng đã hết hạn thanh toán và được hệ thống hủy tự động." in place of the generic cancel alert.
- **Pay page** (`src/app/(checkout)/checkout/pay/[id]/page.tsx`): after `loadOrder`, an order that is expired (CANCELLED with `PAYMENT_EXPIRED`, or PENDING past `payment_due_at`) renders `Result` "Đơn hàng đã hết hạn thanh toán" with a link to the order list and no payment action and no `CreatePayment` call. A COD order renders "Đơn hàng thanh toán khi nhận hàng" and no payment action. A PAID, SHIPPED or COMPLETED order renders `Result` "Đơn hàng đã được thanh toán" with a "Xem đơn hàng" link to `/account/orders/{id}`; a CANCELLED order with any non-expiry reason renders `Result` "Đơn hàng đã bị hủy" with "Đơn hàng đã bị hủy và tồn kho đã được giải phóng." (no 404, even when it never had a transaction). None of these states calls `getPayment` or `createPayment`, and the summary card then shows the order's `totalAmount` and `paymentMethodText`. Otherwise, for a PENDING online order before its deadline, the page calls `getPayment(order)`; when it returns nothing it calls `createPayment(order.id, order.paymentMethod)` (backend returns the existing FAILED transaction when there is one, so the call is idempotent per order) and uses that transaction; `notFound()` remains for an unreadable order or when the create fails. The FAILED phase shows "Đơn hàng vẫn được giữ đến <payment_due_at>, bạn có thể thanh toán lại." The old cancelled-order alert text ("Thanh toán không thành công nên hệ thống đã hoàn tác ... đơn hàng đã bị hủy") is removed. `PaymentSimulator` calls `router.refresh()` after a failed `processMockPaymentAction`, so a payment refused because the order expired in the meantime re-renders the expiry state.
- **Confirm receipt** (new `ConfirmReceiptButton.tsx`, `confirmReceiptAction` in `actions.ts`): on a SHIPPED order the detail header and the buyer list row show "Đã nhận được hàng", also while the order's return request is PENDING or APPROVED (B8: the server allows it); it opens a confirmation `Modal` ("Xác nhận bạn đã nhận được hàng? Sau khi xác nhận bạn có thể đánh giá và đơn không thể hủy."), then calls `ConfirmReceipt`, toasts "Đã xác nhận nhận hàng." and revalidates the buyer list and detail. `FAILED_PRECONDITION` (the system completed it first or it is no longer shipped) is mapped to "Đơn hàng đã được hoàn thành." plus a revalidate so the page shows COMPLETED; any other error shows its message. A SHIPPED order with `auto_complete_at` shows "Tự động hoàn thành vào <date>" when the buyer has not confirmed.
- **Return window**: the return request action appears when `canReturn`; a COMPLETED order with a window shows "Có thể trả hàng đến <date>"; after the window it shows "Đã hết thời hạn trả hàng" and no action. `createReturnRequestAction` maps `FAILED_PRECONDITION` with `rawMessage` containing `return window closed` to "Đã hết thời hạn trả hàng (15 ngày kể từ khi đơn hoàn thành)." and any other `FAILED_PRECONDITION` keeps its server message. The existing review buttons already show on COMPLETED orders and stay.
- **Seller work**: `deriveWorkplaceKpis` replaces "Đơn chờ xử lý" (which counted unpaid online orders) by "Cần gửi" = orders PAID plus orders PENDING with payment method COD, with the number of those whose `ship_by` is before now shown as "Quá hạn: N" and the cell highlighted when N > 0. The seller order list rows and the seller order detail header show "Hạn gửi: <date>" from `ship_by` (an overdue, still-shippable order gets a danger `Tag` "Quá hạn"; no `ship_by` shows "-"). Unpaid online orders are not "to ship".
- **Notification links**: no code change; the notification page renders `linkUrl`. The e2e track verifies that the new-order notification (`/seller/orders/{id}`) and the pay reminder (`/checkout/pay/{id}`) open real pages.
- Pay-page cancelled-order wording and the existing tests that assert "Thanh toán ngay" and "Đơn chờ xử lý" are updated (tasks 2.x and 3.x).
- Tests: colocated vitest; e2e in `platform-e2e/tests/e2e/features/frontend/order_lifecycle_ui.feature` (new). Timers use the compose overlay of the backend slices, never sleeping minutes.

## NFR

- No new request on list, detail or dashboard: every new field rides on the order payloads those pages already load; the dashboard KPI is derived from the existing `ListSellerOrders` call. The pay page adds at most one `CreatePayment` for an order with no transaction, and none for expired, COD or non-PENDING orders.
- Expiry visibility: a buyer sees "Đã hết hạn thanh toán" at the deadline instant (client-independent: computed on the server from `payment_due_at`), and "Đã hủy" within one lifecycle sweep interval (default 1 minute) of it. Confirm receipt shows COMPLETED on the next render (one `revalidatePath`, one round trip; target 2 s, not CI-gated).
- Clock: comparisons use the Next.js server clock; only the server renders deadline decisions, so client clock skew changes nothing. The server (team-order) remains the authority: a button shown a few seconds late or early at a boundary is refused by the backend and the UI refreshes.
- Timestamps display in `vi-VN` locale as today.
- Pre-deploy orders (B7, backfilled by the backend slices): an unpaid order placed before the deploy has no `payment_due_at` and is never auto-expired, so the UI shows no deadline and keeps "Thanh toán lại"; a SHIPPED order gets `auto_complete_at` = migration + 7 days and a COMPLETED order gets `return_window_ends_at` = `updated_at` + 15 days, so both show their dates. The "missing deadline = no deadline, server decides" rule stays for any order the backfill does not cover.

## Data classification

| Field | Class | Purpose | Basis | Retention |
|---|---|---|---|---|
| Order timestamps (`payment_due_at`, `ship_by`, `shipped_at`, `completed_at`, `return_window_ends_at`, `auto_complete_at`) | transactional | show deadlines and windows to the order's buyer or seller | contract necessity | owned and retained by team-order; this UI reads per request, never stores, logs, or sends them to analytics |
| Cancel reason code and label | transactional (buyer free choice among 4 fixed options) | tell the seller and system why an order was cancelled | contract necessity | owned by team-order; the UI keeps no copy |
| Return reason text (existing field) | personal-free text | unchanged | contract necessity | unchanged |

No new personal data is collected or persisted by the frontend. No new analytics event is added: lifecycle actions are not tracked here.

## Threat model

- Assets: the buyer's order and payment state; the seller's ship-by view; the cancel reason code space.
- Abuse: (1) a buyer forging `reasonCode = PAYMENT_EXPIRED` or `ADMIN_FORCE_FAIL` through the server action: the action takes a fixed option key and maps it through a whitelist, so unknown keys are refused before any call, and the backend independently refuses system codes from a buyer with `PERMISSION_DENIED` (B9). (2) A buyer opening another buyer's pay page to create a transaction: `loadOrder` goes through the buyer's token, `GetOrder` is buyer/seller/admin scoped, an unreadable order is `notFound()` before any `CreatePayment`. (3) Pressing "Thanh toán lại" or "Đã nhận được hàng" at a boundary or from a stale page: the buttons are hints only; team-order and team-payment enforce state (`FAILED_PRECONDITION`, CANCELLED transaction) and the UI shows the refusal and refreshes. (4) A seller or other user confirming receipt: the button exists only on the buyer detail (`/account/orders/{id}`), and `ConfirmReceipt` is buyer-only server side (`PERMISSION_DENIED`).
- Authz rule: buyer session required on `/account/orders/**` and `/checkout/pay/**` (unchanged guards, anonymous goes to `/login`); seller scope `listing.write` required on `/seller/**` (unchanged: the seller layout shows "Cần tài khoản Người Bán" to a signed-in session without it and renders no seller page, so no seller order call is made); all ownership is enforced by the gateway and services, never by the UI.
