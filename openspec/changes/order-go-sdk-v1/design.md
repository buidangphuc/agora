## Context

team-order today (main + Q10 + C4 + Q11): `cmd/server/main.go` builds everything by hand (384 lines); `internal/bootstrap` owns the pool, flag client and Kafka handles (`PaymentKafka`, `DisputeKafka`, `OrderEventsProducer`, `kafkaReader`, `kafkaDLQ`); `internal/repository` holds Postgres and in-memory stores side by side; `internal/consumer/run.go` is a hand-written fetch-retry-DLQ-commit loop shared by `PaymentConsumer` and `DisputeConsumer`; `internal/events/relayer.go` plus `internal/repository/outbox*.go` are a hand-written outbox; `internal/upstream` has a metadata-rewriting client interceptor and an audit client; `internal/featureflags` wraps OpenFeature. The reference migration on `origin/feat/go-sdk-v1-e2e` (module path, `internal/app`, `internal/order`, `internal/rpc`, `internal/store`, migrations `0008`-`0018`) is read only; main's behaviour wins, and main already uses migration numbers `0008`-`0010`, so the new migrations start at `0011`.

## Decisions

### D1 Layout (ADR-0016)
`cmd/server/main.go` loads settings with `config.Load()`, then calls `app.Run(ctx, s)` under `signal.NotifyContext`. `internal/app` is the composition root. Build order: logger (`logx`), telemetry (`otelx`), health (`healthx`, check `postgres` only), pool (`postgres.Open`), Kafka producer (`kafkax.NewProducer`), flag client (`flags.New`), upstream connections (domain, identity, promotion, audit), outbox store, repositories, services, handlers, relayer, consumers, sweepers, outbox purge, gRPC server (`grpcx.NewServer`), then `lifecycle.Run`. `cmd/server/main.go` also handles the subcommand `migrate up` (D12) before any of this is built. Binaries: `server` and `resync-commits` (`BINARIES := server resync-commits`). Rename map used to read existing specs and tests: `handler`/`interceptor`/`grpcserver` -> `rpc`; `service` -> `order`; `repository` -> `store`; `consumer` -> `events`; `bootstrap` -> `app`; `featureflags` -> SDK `flags`. Test function names are kept when a test moves, so existing `VERIFIED BY` entries stay traceable by name (D10). Dependency direction: `app` imports everything; `events` imports `store` and `order`; `store` imports neither (the outbox row builders are passed in as options by `app`, as `main` does today); `rpc` imports `order` and `store` types.

### D2 No flags, no fallbacks
`Settings` embeds `sdkconfig.Runtime` and `sdkconfig.GRPC` and names `Postgres`, `OTel`, `Kafka`, `Outbox`, `Flags`, `Audit`, `LogKeyFP`, plus service groups `Events` (topics, groups, DLQs; same env keys as today), `Upstream` (`UPSTREAM_DOMAIN_ADDR`, `UPSTREAM_IDENTITY_ADDR`, `UPSTREAM_PROMOTION_ADDR`; with `Audit.Addr` they are required in every ENV, no default, no fallback mode), `Reservation` and `Lifecycle` (same env keys and values as today). `Upstream` and `Audit` are validated as required in every ENV (the former local defaults `localhost:50051`, `localhost:50053`, `localhost:50061` and the empty-audit local mode are deleted); only `KAFKA_BROKERS` and `LOG_KEY_FP_SECRET` keep a local default and are required in a strict ENV. `order.NewOrderService`, `order.NewCartService` and `rpc.NewOrderHandler` take the saga repository, listing, address and promotion clients, the audit gate and the flag evaluator as required arguments and return an error for nil: there is no vouchers-ignored mode, no flash-price-off mode and no "flags nil means enabled". `app` imports no in-memory store; a source-scan test over `cmd/` and `internal/app` fails on `NewInMemory`, `Noop`, `RequireDurableStorage` and an import of `internal/store/fake`. Test fakes live in `internal/store/fake`.

The lifecycle and reservation duration keys keep their present rule (`RESERVATION_TTL`, `RESERVATION_SWEEP_INTERVAL`, `PAYMENT_DEADLINE`, `PAYMENT_REMINDER_BEFORE`, `LIFECYCLE_SWEEP_INTERVAL`: unusable value -> default plus a boot warning naming the variable; `AUTO_COMPLETE_AFTER`, `RETURN_WINDOW`, `RETURN_AUTO_APPROVE_AFTER`, `SHIP_BY_AFTER`: malformed or non-positive value stops startup naming the key). They are existing requirements of `order-unpaid-expiry`, `order-receipt-completion` and `inventory-reservations`, not dependency flags, so they stay string fields parsed by the existing helpers rather than `time.Duration` fields (which would turn the warn-and-default rule into a refusal).

### D3 Mock data
No mock switch exists in team-order. `MOCK_DATA` is not declared, so the shared strict-ENV mock refusal has nothing to guard here; a stray `MOCK_DATA` in the environment is ignored. If a later change adds a shipping or ETA provider adapter it declares `config.MockData` and a known adapter then.

### D4 Outbox over the existing table
The table `order_outbox_events` keeps its name and its pending rows. SDK `outbox.NewStore(pool, "order_outbox_events")` needs `seq`, `topic`, `traceparent`. Migrations `0012`-`0021` are `outbox.UpgradeSQL("order_outbox_events")` split one file per step: Prepare `0012`; Backfill `0013`; Switch `0014`; check constraint `0015`; validate `0016`; set not null and drop the temporary constraint `0017`; indexes `0018`-`0020`, one statement per file because `CREATE INDEX CONCURRENTLY` cannot run in a transaction; `0021` drops `order_outbox_events_claim_idx` if present and the superseded `idx_order_outbox_claim` (both `DROP INDEX CONCURRENTLY IF EXISTS`). Rollout order (deploy track): scale the old pods to 0 first (a one-time Recreate, never two relayers at once), run the migrate Job (`migrate up`, D12), start the new image; the README says so. Migration `0022` (`order_outbox_v1_requeue_failed`) sets rows parked as `status = 'failed'` by the old `OUTBOX_MAX_ATTEMPTS` rule back to `pending` and resets their attempt counters, so the SDK relayer publishes them; its down step is a no-op. Migration order is `0012`-`0021` upgrade then `0022`, so the requeued rows already carry `seq`. Published rows are purged after 7 days: `events.NewOutboxPurger(store, logger)` returns a `lifecycle.Every(time.Hour, ...)` component whose tick calls `outbox.Store.Purge(ctx, 7*24*time.Hour)`; interval and age are constants, not env keys. The order event rows keep `event_id`, payload bytes and aggregate id, so team-payment, team-notification and team-analytics dedupe is unaffected.

Transactional writes: repositories receive `*outbox.Store` and call `EnqueueTx(ctx, tx, outbox.Row{EventID, AggregateType: "Order", AggregateID: orderID, EventType, Payload: envelope bytes})` inside the transition's own transaction. The existing option functions (`WithPaidOutbox`, `WithCancelledOutbox`, `WithPlacedOutbox`, `WithReminderOutbox`, `WithCompletedOutbox`, `WithReturnOutbox`, `WithReturnRequestedOutbox`, `WithShipmentOutbox`) keep their names but the builder type returns `outbox.Row`. `Topic` is empty so the relayer default `order.events` applies. The in-memory outbox repository and `PendingEvent`, `OutboxRepository`, `OutboxRow` are deleted; outbox tests run against `testkit.Postgres`.

Relayer: `events.NewRelayer(store, producer, s, logger)` in `internal/events/relayer.go` (the only content left of that file) returns `outbox.NewRelayer(store, producer, outbox.RelayerOptions{Topic: s.Events.OrderTopic, Config: s.Outbox, Logger})`, one per process, run as a lifecycle component; the constructor exists so the topic and key wiring is testable in the `events` package. Per-order ordering follows `seq`.

### D5 Consumers
Both consumers become `consume.Handler` functions over `consume.Record`, reusing the decode and apply code of `HandleEnvelope`, mapping `ErrPermanent` to `consume.Permanent(err)`. The hand-written `Run`, `RecordReader`, `DeadLetterProducer`, `RunConfig`, `runLoop`, `processWithRetry` are deleted.

- Payment consumer: `kafkax.NewConsumerClient(s.Kafka, s.Events.PaymentGroup, []string{s.Events.PaymentTopic})`, `consume.Options{DLQTopic: s.Events.PaymentDLQ, KeyFP, Logger}` with the SDK defaults (5 attempts, 100 ms doubling backoff, 30 s ceiling). The group id and topic names are unchanged, so committed offsets carry over.
- Dispute consumer: group `s.Events.DisputeGroup`, topic `s.Events.EngagementTopic`, DLQ `s.Events.EngagementDLQ`, `consume.Options{MaxAttempts: math.MaxInt32, MaxBackoff: 5 * time.Second, MaxPollRecords: 1}`. This keeps the C4 requirement "retry a transient error for the same record until it succeeds, per-attempt delay capped at 5 s, no DLQ, no commit meanwhile" (`order-dispute-refund`, change not yet archived) on the SDK loop. `MaxPollRecords: 1` keeps the poll's work inside the group's rebalance timeout when audit is down for a long time; with one partition owner stuck on one record that is the intended back-pressure. The audit outage does not stop `payment.events`, which has its own client and group.
- Dedupe: `consume.NewDedupe("processed_events")`. Payment and dispute handlers keep their present order: `Processed` read first, effect applied, `Seen` after the effect (design of `order-dispute-refund` "record each processed event_id only after its effect is applied"). Migration `0011` replaces the primary key `(event_id)` by `(consumer, event_id)` so the SDK insert (`ON CONFLICT DO NOTHING` on the pair) works and the same event id is independent per consumer; it runs `ALTER TABLE processed_events DROP CONSTRAINT processed_events_pkey, ADD PRIMARY KEY (consumer, event_id)` in one transaction (the table is small and the lock is brief). Existing rows already carry `consumer`. The `processed_at` column keeps its default.
- The dispute consumer is always started and always has an audit writer (`UPSTREAM_AUDIT_ADDR` is required in every ENV); `events.NewDisputeHandler` refuses a nil gate. `TestDisputeRefundNilAuditWriterNoChange` is deleted with the mode it tested. During a team-audit outage the consumer stalls its partition on one record until audit answers (accepted, see Round 2 item 12).

### D6 Audit first
`upstream.AuditWriter` implements `auditx.Writer` over `auditv1.AuditServiceClient` on the connection from `auditx.Dial(s.Audit, "service-team-order", "audit.write")`; it maps `auditx.Event` to `WriteAuditEventRequest{ActorId, Action, TargetType, TargetId, Metadata}`. The address is required in every ENV, so the connection and the writer are never nil and no nil-writer gate exists. The handler's `auditAdmin` helper is replaced by `gate.Do(ctx, event, func(ctx) error {...})` around the state change; the order of checks is unchanged (authorize, validate input, load, audit, then change), so "audit row exists although the transition was refused" scenarios keep holding: the action's own error (for example `FailedPrecondition`) is returned unchanged. The dispute consumer wraps its change section the same way. The text changes from `audit trail unavailable; action not performed` to `audit trail unavailable`; no client matches on it (the gateway forwards the code).

### D7 Upstream principals
`internal/upstream` keeps one wrapper per client that picks the principal per call with `sdkupstream.WithServicePrincipal`: `serviceStockClient` (domain: `ReserveStock`, `CommitReservation`, `ReleaseStock` -> `service-team-order`/`listing.write`; `GetListing` -> unchanged forwarding, except `listing.read` when `auth.FromContext(ctx)` has no non-anonymous principal), `servicePromotionClient` and `serviceFlashClient` (`ValidateAndReserve`, `CommitReservation`, `ReleaseReservation`, `ReserveFlashSaleStock`, `CommitFlashSaleStock`, `ReleaseFlashSaleStock` -> `promotion.reserve`; `GetActiveFlashSale` and preview-namespace calls forward the buyer). Connections come from `sdkupstream.NewClient(addr)` (request id forwarded, round robin, 2 s bound per call by `DefaultTimeout`). The method-scope safety-net map and `forwardMetadataInterceptor` are deleted because the wrappers always set the principal, so a caller that forgets to mark the context cannot leak the buyer. The old interceptor also gave every other unmarked call with no caller principal the `listing.read` identity (`defaultServiceScopes`); that is dropped on purpose: `GetActiveFlashSale`, the identity address lookups and the preview RPCs run only inside a buyer request (handlers refuse an anonymous principal) and the compensation and sweep paths call only the marked stock and promotion release RPCs and `GetListing`. A call that nevertheless has no principal now carries none instead of a synthesized identity; scenario "Only GetListing gets a synthesized background identity" pins it. `upstreamtest` keeps its fakes. Principal id stays `service-team-order`.

### D8 Errors, auth, health, flags, idempotency
`internal/rpc/errors.go` builds one `grpcx.ErrorTable` from the sentinels the handlers map today (cart and order not found, return not found, status conflicts, `ErrCheckoutInProgress` -> `Aborted`, price changed and stock failures -> `FailedPrecondition`, invalid idempotency key and voucher conflicts -> `InvalidArgument`, upstream transport errors -> `Unavailable`) and every handler returns `grpcx.Status(ctx, logger, err, table)`. The `clientErr(code, msg)` messages that specs pin ("cart is empty", "price changed", "address not found", "checkout is temporarily unavailable", the voucher reasons) stay as explicit `status.Error` values. Principal handling uses `auth.RequirePrincipal` and `auth.RequireScopes`; "owner or admin" (`isAdminOrUser`) stays a service function over `auth.Principal`. `health.Register("postgres", postgres.Checker(pool))` only: Kafka is not a readiness check, and the SDK has no upstream checker, so none is registered; `lifecycle.Run` with `OnShutdown: health.Drain` and `lifecycle.StopAfter(grpcx.Serve(srv, s.GRPC), relayer, paymentConsumer, disputeConsumer, reservationSweep, lifecycleSweep, outboxPurge)`. The checkout kill-switch is `flags.Evaluator.BooleanEnabled(ctx, "checkout-enabled", true)`; `flags.New` runs once in `app` and its `Close` is pushed on the lifecycle stack. `order.NormalizeIdempotencyKey` becomes `strings.TrimSpace` + `idempotency.Validate`, wrapping `idempotency.ErrInvalidKey` (still mapped to `InvalidArgument`); `IdempotencyKeyMetadata` and `MaxIdempotencyKeyLen` are replaced by `idempotency.MDKey` and `idempotency.MaxLen`.

### D9 Sweepers and compensation retry
`runReservationSweeper` and `runLifecycleSweeper` become `lifecycle.Every(interval, fn, lifecycle.WithLogger(logger))` components; the adapters call `SweepExpiredReservations(ctx, now)` and `SweepLifecycle(ctx, now)` (which log their own failures) and return nil, so a failed sweep is retried on the next tick as today. The `cmd/server/lifecycle_sweeper_test.go` tests move to `internal/app` with names kept. Compensation: `releaseReservationWithRetry` keeps its name and its place in `releaseOrPark`, but its hand-written loop becomes `resilience.Do(ctx, fn, resilience.Retry(RetryOptions{MaxAttempts: releaseCfg.maxAttempts, BaseDelay: releaseCfg.backoff, RetryIf: retryable}))` where `retryable` accepts only `Unavailable` and `DeadlineExceeded`. Baseline today: 3 attempts (`defaultReleaseMaxAttempts`), any error retried, delay `backoff x attempt`, `WithReleaseRetry(timeout, maxAttempts, backoff)`, per-release timeout 30 s and a 2 s inline budget on buyer cancel (`defaultInlineReleaseTimeout`). Kept: the 3-attempt default, `WithReleaseRetry` and its semantics, the per-release timeout, the 2 s inline budget, parking `RELEASE_FAILED` after the last failure. Changed (accepted behaviour change): only transient codes are retried, so a non-retryable code is attempted once instead of 3 times, and the delay follows the SDK backoff instead of the linear one. Tests that count release calls for a non-retryable code (`cancel_test`, `lifecycle_test`, `sweep_test`, `platform_release_test`) update their expected count from 3 to 1; tests that use `WithReleaseRetry` keep working unchanged. `ReleaseFlashSaleStock` (`releaseFlashHolds`, `releaseOrderFlashHolds`) and `ReleaseReservation` stay best-effort and logged, never retried or parked, as before.

### D10 Traceability of moved tests
Existing specs cite `internal/handler`, `internal/service`, `internal/repository`, `internal/consumer`. Test names are preserved; only the package path changes, per the rename map in D1. This change MODIFIES a spec only where it describes a removed flag, fallback or env var (`order-admin-audit`: the four admin-action requirements lose their no-audit-client wording and their no-client scenarios become boot-refusal scenarios (same titles, because a MODIFIED block must keep every title), and the audit-client requirement likewise; `order-advertised-price`: the flash principal requirement loses its nil-client-set sentence and its unset-address scenario becomes a boot refusal, and the AddToCart requirement is replaced). The shared `deploy-runtime` requirement is not touched here (Round 2 item 3). Scenarios of the unarchived changes `order-multishop-checkout` ("Vouchers are ignored without a promotion client") and `order-address-eta` (nil address client) cannot be MODIFIED from here because they are not in `openspec/specs`; see "Cross-change dispositions".

### D12 Migrations are a subcommand (Round 2 item 1)
`migrations/embed.go` embeds `*.sql`. `cmd/server/main.go` reads `os.Args`: `migrate up` calls `config.Load()` for `DATABASE_URL` and `migrate.Up(ctx, url, migrations.FS)` and exits 0 or 1; any other first argument exits 2 with usage; no argument runs `app.Run`. `app.Run` never calls `migrate`. Compose keeps the service `team-order-migrate` running the service image with command `migrate up`; gitops gets an Argo PreSync Job per service running the same command (deploy track, change deploy-go-sdk-v1).

### D11 Tests and fakes
The Postgres test helpers in `internal/store/pg_helpers_test.go` are replaced by `testkit.Postgres` and `testkit.Schema`; the DLQ in consumer tests is `testkit.Recorder`; consumers are driven through `consume.Consumer` over a fake group client for loop-level scenarios and called as handlers for apply-level scenarios. Docker-backed tests must run: a skipped test is a gate failure (`GO_SDK_REQUIRE_DOCKER=1`, and the gate fails on any `SKIP` line).

## Risks

- Outbox upgrade on a live table: mitigated by the scale-old-pods-to-0-first rollout (Recreate once) and the order-preservation test (scenario "The outbox upgrade keeps pending events in order").
- `processed_events` primary key swap takes a short `ACCESS EXCLUSIVE` lock; the table is write-light (one row per consumed event) and the migration is one transaction.
- Dispute consumer with `MaxAttempts: math.MaxInt32` and `MaxPollRecords: 1`: a long team-audit outage parks that one partition on one record until audit answers (the C4 requirement); if the group's rebalance timeout is shorter than the outage the member is removed and another member retries the same record, which is safe because the transition is a compare-and-set.
- `go mod download` in the Docker build now reaches the public module proxy for the SDK tag; the build context stays `./team-order` and needs no sibling directory.
- Requeueing old `failed` rows (migration `0022`) republishes events that may have been parked for a long time; consumers dedupe on `event_id`, so a replay is a no-op downstream.
- Retry on compensation releases can double the number of release calls to team-domain and team-promotion during an outage; both are idempotent on reservation id.
