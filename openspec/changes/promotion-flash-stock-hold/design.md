## Context

Voucher holds already exist: `voucher_reservations` (migration 0001), `ReservationRepository`, `VoucherService.ValidateAndReserve/CommitReservation/ReleaseReservation`, saga RPCs gated by `RequireService(ScopePromoReserve)`. The voucher repository takes no lock because it does not check a counter at reserve time. Flash stock does, so the flash hold needs a transaction with a row lock.

## Decisions

- **Hold table, not a counter column.** `flash_sale_holds` keeps one row per reservation (like `voucher_reservations`), so idempotency is a `UNIQUE(reservation_id)` and release needs no arithmetic on a shared counter. `held = SUM(quantity) WHERE campaign_id = $1 AND status = 'reserved'`. Why: a retried release can never drive a counter negative; the sum is derived and cannot drift. Alternative (a `stock_held` column) rejected: two writes per transition and a drift risk.
- **Concurrency by campaign row lock.** Reserve and commit run `SELECT stock_cap, stock_sold, ... FROM flash_sale_campaigns WHERE id = $1 FOR UPDATE` inside the transaction before reading holds. Concurrent reserves for one campaign serialise; reserves for different campaigns do not. Why: simplest correct invariant; a unique-index or serialisable-retry design is more code for the same result at flash-sale scale per campaign.
- **Idempotent reserve order:** first look up the `reservation_id`; if found, return the stored outcome (`reserved=true` for active or committed; `reserved=false, reason=not_active` for released or expired) without rechecking the window, price or stock, and ignoring any differing request fields (replay with different fields returns the stored outcome; chosen over refusing because team-order retries must stay harmless; Clarifications Q5 guarantees ids are never reused for a different line). Otherwise lock and check. Insert uses `ON CONFLICT (reservation_id) DO NOTHING` so two racing first calls with one id create one hold.
- **Reason order.** `not_active` (existence, window, kill-switch, listing/variant), then `price_changed`, then `insufficient_stock`. Reasons are the closed set owned by `q5-flash-stock-contract`.
- **Refusals are responses, not errors.** `reserved=false` + `reason`, as the contract says; gRPC errors only for bad input, authz and infrastructure (`INTERNAL`, generic message). team-order maps `reserved=false` to its "price changed" refusal.
- **Variant rule.** A campaign with empty `variant_id` covers every variant of the listing; a campaign with a `variant_id` covers only that variant. The request `listing_id` must equal the campaign's. Why: mirrors Initiative story 1 edge case.
- **Active window:** `starts_at <= now < ends_at`, a zero bound is open-ended (same as `active()` in the in-memory repository and `GetActiveByListing`). Kill-switch OFF = not active. `nowFn` is the existing injectable clock.
- **Commit does not recheck the window or the kill-switch.** A hold taken while the sale was active is honoured if committed within its 15 minutes. Commit moves `reserved -> committed` and adds the quantity to `stock_sold` in one transaction; `held` drops by the same amount, so `remaining` does not change at commit.
- **Release/commit results:** release of unknown = `released=false`; of an active, committed, released or expired hold = `released=true` (counters change at most once). Commit of unknown, released or expired = `committed=false`; of a committed = `committed=true`.
- **Hold lifecycle (human answer, Clarifications Q1).** A hold expires 15 minutes after reserve (`expires_at`, equal to the team-domain reservation TTL). Expiry is evaluated at read: an active hold is `status = reserved AND expires_at > now`, so expired holds stop counting in `remaining` and cannot be committed with no background job. Commit is called by team-order in checkout Phase B (not on OrderPaid). Release works for an active hold and for a committed hold (`stock_sold -= quantity`, once); `CancelOrder` calls it. Released and expired rows are purged 30 days after they became terminal; committed rows are never purged (kept until the campaign is deleted by cascade) so a late `CancelOrder` release still works.
- **E2E driving of service-only RPCs.** The gateway does not route them and team-promotion publishes no host port. The helper `support/flash_hold_support.py` runs `grpcurl` from a throwaway container (`docker run --rm --network <stack_network from plp_stack> fullstorydev/grpcurl -plaintext -H 'x-principal-id: service-team-order' -H 'x-principal-type: service' -H 'x-principal-scopes: promotion.reserve' team-promotion-svc:50061 ...`), the same headers the interceptor reads. A user principal is simulated with `x-principal-type: user`. Same pattern as `prm_pay_stack.py`. The user-through-gateway check posts the Connect path and asserts the call is refused (any 4xx; the exact code depends on gateway route policy). Expiry in e2e is asserted by backdating `expires_at` of the hold row with `plp_stack.psql` on the promotion database (the test cannot wait 15 minutes).

## Risks

- Expiry at read means a stale `reserved` row lingers until purged (30 days); harmless because every query filters on `expires_at`.
- Hot-row contention on a very popular campaign: accepted, bounded by transaction time (a few ms).
- The Postgres repository test reads migration files by path (`postgres_test.go` loads `0001`); it must also load `0004` or the hold tests fail to find the table.
