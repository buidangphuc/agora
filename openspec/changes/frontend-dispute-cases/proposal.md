## Why

Initiative q6-trust-enforcement gives a buyer whose return was rejected or ignored a way to escalate to Agora, and gives admins a dispute inbox. The backend half (engagement `return_id`, `ListOrderDisputes`, `ListDisputes`, `ruling`, the refund consumer in team-order) has no UI. Without it a buyer cannot reach the escalation, and an admin has to call `ResolveDispute` by hand. This slice adds the buyer button "Khiếu nại lên Agora" with the order's dispute list, and the tab "Khiếu nại" of `/admin/cases`.

initiative: q6-trust-enforcement

depends_on: frontend-listing-moderation (creates `src/app/(shop)/admin/cases/`, its page gate, tab strip and the `ConsumerShell` admin link) and order-dispute-refund (and transitively engagement-dispute-escalation). Both build only after q10-order-lifecycle has merged to main: this slice reads `OrderReturn.can_escalate` (q10 order-receipt-completion) and edits `src/features/order/OrderDetailView.tsx` / `ReturnRequestSection.tsx` after q10's frontend-order-lifecycle.

## What Changes

- Buyer, order detail (`/account/orders/[id]`, returns tab):
  - Each return carries `canEscalate` (mapped from `OrderReturn.can_escalate` in `src/lib/gateway/orders.ts`). When it is true and no OPEN or INVESTIGATING dispute is linked to that return, the return card shows the button "Khiếu nại lên Agora". The button opens a modal with a reason field (required, trimmed) and a submit; no evidence upload (evidence URLs are not offered).
  - Submit calls `EngagementService.CreateDispute` with `order_id`, `defendant_id = order.sellerId`, `return_id`, `reason`, through a server action. Result states are mapped to Vietnamese messages for `FAILED_PRECONDITION`, `ALREADY_EXISTS`, `PERMISSION_DENIED`, `NOT_FOUND` (unknown return, return of another order, or an order the caller cannot see), `INVALID_ARGUMENT` (defendant is not the order's seller, i.e. a stale page) and outage (`UNAVAILABLE` or a 5 s timeout); the modal keeps the typed reason on every refusal. A return whose dispute is RESOLVED or REJECTED can be escalated again while `canEscalate` is true (00-spec A18).
  - A section "Khiếu nại" under the returns tab lists the order's disputes (`ListOrderDisputes`, newest first) with status, ruling, return link and the admin resolution text. A failed list call degrades only that section. `ListOrderDisputes` is also allowed to the order's seller (A18); a seller-side view is not in this slice.
- Admin, `/admin/cases` tab "Khiếu nại" (the tab strip and gate come from frontend-listing-moderation; this slice adds the tab `?tab=disputes`):
  - Server-rendered list from `ListDisputes`, filter by status (default OPEN), oldest first, 20 per page, "Trang sau" link with the cursor; deep link `?tab=disputes&dispute=<id>` loads that dispute through `GetDispute`.
  - Row detail: order id (plain text), claimant, defendant, reason, evidence URLs (links only when scheme is `http` or `https`), linked return id, status, ruling, resolution.
  - Actions follow the server state machine: OPEN offers "Bắt đầu điều tra" (INVESTIGATING) and "Từ chối"; INVESTIGATING offers "Cập nhật ghi chú" (INVESTIGATING), "Giải quyết" and "Từ chối". OPEN to RESOLVED is not offered. For a return-linked dispute "Giải quyết" requires a ruling (Người mua thắng / Người bán thắng); choosing "Người mua thắng" shows a confirmation that the return will be approved and, for an order paid online, refunded (a COD order stops at APPROVED; COD refunds are a follow-up, 00-spec M2). A dispute without a return offers no ruling. A ruling is sent only with RESOLVED (A17).
  - After a successful action the panel shows that dispute's detail at `?tab=disputes&dispute=<id>` (through `GetDispute`) with its new status and actions, so a dispute that left the current filter stays on screen.
  - Calls `ResolveDispute` through a server action; the audit-first failure (`UNAVAILABLE`) is shown as "no change made"; a 5 s timeout is shown as "state unknown, reload", since a timeout does not prove nothing was saved.
- New gateway client functions in `src/lib/gateway/disputes.ts` (`server-only`), server actions in `src/features/dispute/actions.ts`, views in `src/features/dispute/` and `src/features/admin/DisputeCasesPanel.tsx`. `makeClients` already has the `engagement` client; no change.
- Gateway routes: `CreateDispute`, `GetDispute`, `ResolveDispute` are already edge-routed (`team-gateway/internal/edge/engagement.go`; `ResolveDispute` is admin-only in `policy.go`). `ListOrderDisputes` and `ListDisputes` are added to the forwarder and policy by engagement-dispute-escalation, not here; this slice makes no gateway change.
- No new dependency. The proto copy in `team-frontend/proto` is regenerated by q6-trust-contract; this slice only runs `npm run proto`.

## NFR

- Admin tab render is one `ListDisputes` call after the session check (p95 budget 300 ms at gateway, non-gating); client timeout 5 s as in `audit.ts`; a timeout maps to the "load error" state, not a crash.
- Order detail adds one `ListOrderDisputes` call, run in parallel with the existing returns load; its failure or a 5 s timeout hides only the dispute section, never the order.
- Resolve and create are single-flight: the submit control is disabled while the action is pending, so a double click sends one request.
- Availability: team-engagement down degrades the dispute section and tab only. No client JS is needed to read the admin list; actions need JS.

## Data classification

- Dispute fields shown: claimant id, defendant id, order id, return id, `reason` and `resolution` (free text, may contain personal data the buyer or admin typed), `evidence_urls` (buyer supplied URLs). Purpose: complaint handling; basis: contract performance and platform duty to handle complaints (Decree 85/2021, Decree 13/2023 processing record); retention: team-engagement policy, the frontend stores nothing.
- Reason and resolution text travel only through server actions to the gateway; they are not sent to the tracker or analytics, not placed in URLs, not logged client-side. The deep-link query carries a dispute id only.
- Evidence URLs are rendered as text and as a link only for `http`/`https`, with `rel="noopener noreferrer"` and `target="_blank"`.
- No new cookies, local storage or client persistence. The bearer stays server-side.

## Threat model

- Assets: the dispute record (reason, evidence), the refund a buyer-favour ruling triggers, the admin session token.
- Abuse cases:
  1. A buyer opens the escalation for someone else's order or return: the UI only offers it for returns of the buyer's own order, and team-engagement checks the party and `can_escalate`; `PERMISSION_DENIED` or `FAILED_PRECONDITION` is shown as the matching message, nothing is created.
  2. A non-admin opens `/admin/cases?tab=disputes` or calls the resolve action: the page shows the 403 result without any gateway call; the server action re-checks the `admin` scope before calling and the gateway enforces `admin` on `ResolveDispute`, `ListDisputes`.
  3. A forged `javascript:` evidence URL: only `http`/`https` URLs become links; others are shown as plain text.
  4. Script or markup in reason, resolution or evidence: rendered as React text, never as HTML.
  5. Double click or replay of a buyer-favour resolve: the control is single-flight; the server rejects a second resolution (`FAILED_PRECONDITION`) and the refund is once per return id (team-order).
  6. Mis-click on a money action: buyer-favour needs an explicit confirmation step naming the approval and the online-paid refund.
  7. Cursor or `dispute` query tampering: both are opaque and passed through; invalid values yield the empty or not-found state, never a crash.
- Authz rule: admin tab and actions render only when `principal.scopes.includes("admin")`; the escalation button renders only for the order's buyer on a return with `canEscalate`. Enforcement is at the gateway and team-engagement, the UI gate is presentation only.

## Open assumptions

- The tab mechanism of `/admin/cases` (query param `tab`, value `disputes`) is defined by frontend-listing-moderation; this slice follows whatever it ships and the value `disputes` is assumed.
- q10's frontend-order-lifecycle adds no dispute UI (dropped by the q10 planner); `ViewOrderReturn.canEscalate` is added here, not there.
- The server has no limit on dispute `reason` length today (team-engagement checks none; engagement-dispute-escalation keeps limits unchanged); the UI caps it at 1000 characters (assumption to confirm; a server-side cap belongs to engagement-dispute-escalation).
