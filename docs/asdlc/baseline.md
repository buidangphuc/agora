# ASDLC baseline (W0-5)

Source: git history at HEAD `aff5b17d78fe`, archive dates start .. HEAD. Generated by `scripts/asdlc/baseline.py`; raw data in `metrics/baseline.json`.
Purpose: the "before" numbers that W5-1 compares against.

## Method

- **Change set**: every `openspec/changes/archive/<date>-<id>/` directory at HEAD (filtered by archive date).
- **start**: author time of the earliest commit that added `openspec/changes/<id>/proposal.md` (searched with `--no-renames`, so the later move into `archive/` does not hide it).
- **end**: author time of the earliest commit that added `openspec/changes/archive/<date>-<id>/proposal.md`.
- **cycle time** = end - start, in hours. Only changes whose proposal was committed *before* the archive commit are *measurable*; the rest are `archive_only` / `same_instant` and are excluded from the percentiles (counted in `n_archive_only`).
- **affected repos**: top-level directories (excluding meta dirs: `docs`, `gates`, `metrics`, `openspec`, `plan-analytics`, `plan-mlops`, `plans`, `scripts`) that are either (a) mentioned as a path-like token in the archived artifacts (proposal/design/tasks/specs), or (b) touched by any commit whose message mentions the change id.
- **commits in window** (size proxy): non-merge commits with start <= time <= end that touch an affected repo.
- **post-merge fix**: non-merge commit with a conventional `fix` / `fix(scope)` subject, strictly after `end` and within 14 days, touching at least one affected repo.
- **fix rate** = share of changes with >= 1 post-merge fix, over changes whose 14-day window is complete (end + 14d <= newest commit); `fixes_per_change` uses the same set.

## Caveats (read before quoting a number)

1. **Archive-only changes.** Changes archived in the first snapshot commits (2026-09-04) and a few later batches never existed under `openspec/changes/<id>/` in history, so they have no start. They are listed but excluded from cycle time.
2. **Batch proposals.** Many proposals were committed in one batch (e.g. 13 on 2026-09-20, 13 on 2026-10-08) while the work started earlier or was done in a different order; cycle time is then "proposal committed -> archived", not "work started -> shipped". It is a proxy, probably an underestimate of lead time and an overestimate for changes queued behind others in the same batch.
3. **Single-author, agent-assisted history.** Timestamps reflect commit time, not working time; overnight/idle gaps are included. The slowest changes (about 20 days) are the 2026-09-20 proposal batch archived around 2026-10-10 after a pause; their cycle is mostly queue time, not build time.
4. **Fix heuristic is repo-level, not change-level.** Fix commits are not linked to a change; any `fix` commit on a shared repo (team-ai, platform-gitops, ...) in the window counts. Overlapping changes in the same repo therefore share each other's fixes (over-count), and fixes mislabelled as `feat`/`chore` are missed (under-count). Treat it as an upper-bound-ish trend indicator.
5. **Fixes that belong to the change itself.** Fixes made between start and end are not counted (they are in the window size); only fixes after archive are.
6. **Right censoring.** Changes archived in the last 14 days before HEAD have an incomplete window and are excluded from the fix rate.
7. **Repo detection** from text can miss a repo the change touched without naming it, or add one it only referenced. Changes with no detected repo get 0 fixes and `commits_in_window` null.
8. The history itself is short (about 5 weeks, ~1k commits); percentiles over ~60 measurable changes are indicative, not statistically tight.
